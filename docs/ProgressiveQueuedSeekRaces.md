# Конкурентные команды ожидающего перехода

9 ноября 2026. Проверка [очереди 1.87](ProgressiveQueuedSeek.md) и её
[таймлайна](ProgressiveTimelineSeek.md) обычными main EXE трёх редакций.
Harvester, публичный API и SDK не меняются. Стенд использует частные профили,
подтверждённые локальные данные, отдельные IPC-соединения и настоящие декодеры.

## Парные команды

Два потока начинают запросы у barrier; каждый вызов открывает собственное
IPC-соединение. Проверяются одинаковый старт и смещения ±3 ms. Сохраняются
время начала/конца каждого запроса и полные ответы. Это наблюдаемая гонка
публичных команд, а не принудительный выбор внутренних моментов I/O.

По четыре повтора каждой пары:

- новая цель / другая цель;
- новая цель / cancelSeek;
- новая цель / Stop;
- новая цель / Cancel remux job;
- новая цель / release активного output reader;
- новая цель / открытие обычного локального файла с replace;
- новая цель / ошибка обязательного потока;
- публикация доступного диапазона / cancelSeek;
- публикация / новая цель.

Для недоступных целей `seekRevision` определяет последнюю принятую цель.
Отклонённый или отменённый запрос не расходует quota. При одновременной
публикации decoder может успеть принять прежнюю цель до новой команды:
два фактически применённых перехода расходуют две попытки. Cancel после
применения не делает обратный seek. Тест сохраняет оба допустимых порядка,
проверяя конечную позицию и quota, а не предполагает нужный порядок по времени
завершения клиентских вызовов.

Stop/Cancel/release/error/replace должны очистить pending target. Поздние
команды старого playbackId не воздействуют на обычный replacement. Независимый
endpoint всё время сохраняет playbackId, позицию ручной паузы и readerIds.
Исходники медиа не меняются. Close требует release/filesClosed; затем forget.

## Ограниченный стресс очереди

Один main процесс выполняет четыре warmup и 100 измеряемых циклов. Каждый цикл
создаёт growing AAC job, действительно запускает decoder и ставит на паузу.
Выполняются 16 пар конкурирующих смен/отмен целей: новые readerIds при ожидании
появляться не должны, quota/позиция не меняются. Затем выполняются два настоящих
растущих перехода и один из Stop/Cancel/readerRelease/producer failure.
Активный output reader после reload выбирается по текущему filesClosed/released
proof, а не по первому историческому ID.

В первом измеряемом цикле проверяются все 16 применений, отказ следующего
queued target с continuous-seek-limit и прежний completed seek после complete.
Каждый цикл заканчивается filesClosed/forget и настоящим выходом принадлежащего
ему worker. Оба main PID сохраняются; источник второго endpoint остаётся на паузе.

Ресурсы записываются после каждого цикла. Окна early 1–10, steady 31–40 и late
91–100 проверяются прежними порогами lifecycle-стенда: late handles ≤ steady+8,
threads ≤ steady+2 и early+8, RSS/private ≤ early+256 MiB, средний parent CPU
последних десяти циклов ≤1 ядра. Окна и baseline сохраняются **до** assert.
Парные IPC запросы и SDK close сохраняют прежний бюджет 2 s. Полная latency
приёмка, startup deadline и многочасовая работа этим тестом не объявляются.

Это один AAC-LC stereo/48 kHz/fractional-H.264 профиль и частный software/null
вывод; предыдущая codec matrix не заменяется этим срезом. Classic — Null Video
Renderer (Uncompressed) только в тестовых INI. Физический A/V, desktop renderer,
аппаратное оборудование, Wayland и вся race/stress matrix не входят в срез.

Результаты и точные native exits:
[отчёт](https://github.com/LiberVixer/FoxicMP/blob/main/docs/ProgressiveQueuedSeekRacesValidation-2026-11-09.json).


## Как повторить

Для Qt CMake/CTest регистрирует `progressive-continuous-queued-races` и
`progressive-continuous-queued-stress`. Linux запускается только через
`qt/tests/run_tests.sh` с частными X11/D-Bus/PulseAudio. Обычные main-пакеты
также проверяются `tests/progressive_aac_package_test.py` с `--scenario
queued-races` или `--scenario queued-stress`; SDK-directory должен указывать
на проверенные модули 1.87. Для Classic нужны отдельная копия, безопасный INI
контекстного меню и `--classic-null-video`; установленный профиль не подходит.

Исходный ресурсный oracle и пороги берутся из
`tests/progressive_continuous_lifecycle_stress.py`. Никакие значения порогов
и квота receipts не расширяются ради этого прогона. В каждом цикле сохраняются
metrics до/после отказа; при первом исключении первичная ошибка не подменяется
ошибкой очистки. Результат Linux не считается результатом Windows.

## Конечные результаты

Каждая редакция прошла 36 парных сценариев, четыре warmup и 100 измеряемых
циклов. Всего 408 основных cases и 12 warmup; 5100 пар конкурентных запросов
с учётом warmup. Конечные native test drivers exit 0. Внедрённые producer errors
и очистка принадлежащих тесту idle main peers имеют отдельные process exits;
их не объявляют штатными exits 0.

Для основного процесса показатели steady → late:

| Редакция | Handles | Threads |
| --- | ---: | ---: |
| Linux Qt | 38 → 38 | 60 → 60 |
| Windows Qt | 1699 → 1696 | 38 → 37 |
| Windows Classic | 477 → 469 | 15 → 13 |

Оба endpoint каждой редакции прошли также RSS/private/CPU gates. Полные окна
измерений, reader proofs, SHA бинарников/SDK/исходников и время запросов сохранены
в отчёте. Чтобы не повторять одинаковые объекты тысячами раз, stress rounds
записаны массивами с общей схемой `stressRoundColumns`; полный сырой отчёт
каждого прогона привязан SHA-256. Это не доказывает отсутствие утечек в длительной
работе и не закрывает прежние необъяснённые отказы общей resource/latency приёмки.

Новых ошибок приложения этот ограниченный прогон не выявил; production-код,
SDK-модули, EXE и INI не менялись. Linux проверялся на установленном EXE.
Все 587 защищённых файлов и 158 HKCU shell entries совпали до/после. Изменены
только тесты, CTest-регистрация и документационная упаковка SDK; новая сборка
приложения и переустановка не требуются. Harvester не менялся, новых внешних
задач/таймеров не создавалось.
