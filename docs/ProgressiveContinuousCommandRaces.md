# Continuous SDK 1.82: публикация, Stop и замена просмотра

Проверяются четыре пары одновременных запросов через обычный IPC:
`continuousRemuxUpdate`/Stop, update/замена видео, `readerRelease`/замена и
`continuousRemuxCancel`/замена. Для каждой пары выполняются четыре варианта
отправки из двух потоков: общий barrier и смещение 0/−3/+3/0 ms. Через раз
исходный просмотр вручную поставлен на паузу.
[Результаты, SHA и исходные отказы](ProgressiveContinuousCommandRacesValidation-2026-11-04.json).

Финальные прогоны прошли: **по 16 сценариев каждой редакции, всего 48**, каждый
exit code 0. Windows Qt дополнительно прошёл тот же набор через зарегистрированный
CTest. На каждой Qt ОС прошли 13 выбранных CTest-групп и ещё две multi-reader
регрессии; native `progressive-media` содержит 469 проверок на ОС, включая новый
детерминированный сценарий. Classic проверен отдельным прогоном настоящего
IPC/DirectShow на пересобранном MSVC EXE.

## Найденная ошибка и исправление

Первый Windows Qt прогон остановился при release/замене: повторное открытие
исправного fMP4 получило `source_not_ready: Cannot read confirmed MP4 header`.
Отдельный native-тест детерминированно воспроизвёл причину: удержание `.guard`
реестра readers при открытии давало ту же ложную ошибку заголовка. Его baseline
exit code — 1; исходный Windows Qt прогон также завершился exit 1. Эти результаты
сохранены, не заменены последующими успешными.

Общий `Fmp4V2Bridge::exact` теперь сохраняет код `reader_registry_busy` от
ResourceSource. Это временная занятость реестра, которую вызывающая сторона
может обработать отдельной попыткой. Параметры воспроизведения, defaults, SDK и
публичные actions не меняются. Ожидание или автоматический повтор Play в плеер
не добавляются. Изменение применяется к общему Qt и Classic-коду.

Native-тест удерживает настоящую блокировку, требует именно
`reader_registry_busy` без оставшегося reader, затем снимает блокировку,
открывает тот же источник, сверяет байты и закрывает leases. Он входит в
`progressive-media` наряду с прежними проверками контейнеров и codec headers.

## Проверяемое поведение

Каждый сценарий начинает настоящий continuous просмотр до complete. Тестовый
writer физически дописывает partial и готовит новые ranges/SHA перед гонкой.
Один запрос может успеть до другого: update либо принимается, либо получает
`continuous-closed`. Времена начала/конца обоих клиентских запросов записываются;
наличие barrier не выдаётся за заданный порядок внутренних инструкций.

При замене асинхронная подготовка может быть отменена до commit закрытием старого
просмотра (`preparation_cancelled`) или отклонена при краткой занятости реестра
(`reader_registry_busy`). Стенд допускает только эти конкретные причины и
выполняет следующий **явный** start с ограничением времени. Другие ошибки,
включая ложное повреждение заголовка, проваливают тест. Отменённая подготовка
не должна позднее самостоятельно запускать decoder.

Проверяются настоящий новый просмотр, закрытие старых decoder readers и source,
`filesClosed` receipts, отсутствие старого private cache. Уже после commit новой
сессии повторяются старые Stop/cancel/readerRelease/update. Новое видео должно
продолжать кадры с тем же readerId. Второй независимый процесс также продолжает
просмотр с прежними IDs. Исходные файлы после записи writer не меняются плеером;
все сценарии выполняются в том же живом процессе.

## Проверка и поставка

Новый CTest — `progressive-continuous-sdk-command-races`, timeout 180 s.
Linux использует `qt/tests/run_tests.sh` и частные X11/D-Bus/PulseAudio. Classic
использует две отдельные защищённые копии с `ContextMenuPrompted=1` и
`ContextMenuEnabled=0` до запуска, без открытия страницы «Форматы». Установленные
Windows EXE/INI и 158 HKCU shell entries сверяются до/после. Одноразовая задача
и её тестовые копии удаляются. Harvester и публичные SDK ZIP не меняются.

Все три main EXE пересобираются. Проверенная Linux-сборка устанавливается
атомарно, с предыдущим EXE для отката и проверкой неизменности INI/личных файлов.
Точные exit codes, результаты native/GUI/SDK регрессий и квитанция установки
приведены в отчёте.

## Граница

Это ограниченная матрица публичных команд локального MP4/H.264 video-only
continuous профиля. Она не задаёт смерть worker в конкретной инструкции pipe/file
I/O и не заменяет длительный stress, все варианты schedule, surviving external
readers, другие codecs/containers или полную приёмку ТЗ. Прежний единичный Linux
heartbeat release >2 s остаётся открытым.
