# Проверка media cache / leases — 30 октября 2026

Проверен [внутренний режим большого каталога](ProgressiveCatalogCache.md).
[Машинный отчёт](ProgressiveCatalogCacheValidation-2026-10-30.json) сохраняет
сценарии, SHA исходников/runner, точные exit codes и неудачные попытки.

Одинаковые **15 сценариев** прошли в Linux GCC, Windows MinGW GCC и Windows
MSVC x64, exit 0. Это native I/O/reader-тесты, не три playback-теста приложений.

- 200 последовательных ресурсов: одновременно не более восьми активных leases;
  старые закрытые квитанции не исчерпывают общий лимит registry 128.
- После заполнения кэша общее число OS handles не растёт при дальнейших чтениях.
  LRU сохраняет недавно использованный файл, вытесняет другой; повторное открытие
  получает новый reader ID. Живую квитанцию нельзя забыть раньше закрытия.
- Метаданные 8192 ресурсов: открываются только запрошенные файлы.
- Подмена вытесненного файла идентичными байтами, перезапись, truncation и
  исчезновение полного файла выявляются при возвращении к ресурсу.
- SHA-256 обязателен только в новом режиме. Старый inline-режим по-прежнему
  удерживает все 16 прочитанных ресурсов в отдельном совместимом сценарии.
- Добавление ресурсов, отказ некорректному update без потери текущего источника,
  предел 16 MiB, запрет retired, EOF/offset, отмена и последний shared owner.
- Пока удерживается последний owner, восемь финальных leases активны; после
  его освобождения все имеют `filesClosed=true` / `released=true` и могут быть
  явно забыты обычным reader API.

Linux: CTest 8/8, exit 0 до финального уточнения policy нового режима. Помимо нового кэша пройдены модель 90, сегменты 11,
каталог 51, страницы 25, прежний ResourceSource 30, integrity 10 и старое
сегментное чтение 295. На Windows шесть прежних групп прошли в общем прогоне,
I/O-кэш повторён после исправления ожидания теста; 295 сегментных проверок
повторены отдельно с exit 0. Списки 295 проверок Linux и Windows совпадают.

При финальном review ограничение 16 MiB распространено также на подтверждённые
диапазоны ресурсов с неизвестной полной длиной. После этой правки повторены
15 cache-сценариев на всех трёх компиляторах; на Linux также ResourceSource и
integrity — CTest 3/3, exit 0. Прежний Inline-path этим уточнением не изменён.

Первая Linux-фикстура ограничения размера была одновременно неполным `complete`
ресурсом и закономерно отклонялась общей моделью раньше cache policy, exit 1.
Другая проверка ожидала `invalid-read` для длины >65536, хотя private test CLI
отклоняет такую команду раньше как `invalid_snapshot`: Linux/MSVC exit 1,
Windows CTest exit 8. Исправлены тестовые ожидания, не защита кэша.
Исходный общий Windows-прогон не переименован в exit 0: отчёт явно хранит exit 8
и отдельный успешный повтор нового теста.

Новый режим пока не выбирается публичным IPC/CLI или playback bridge. Нет
доказательства декодирования/перемотки большого каталога, сохранения A/V sync,
запуска через Harvester или готовности live retirement. `filesClosed` может
ждать registry guard; этот прогон не доказывает deadline для такого ожидания
или зависшего syscall. SHA проверяет затронутые блоки; закрытые ресурсы не
сканируются постоянно.

Harvester, HKCU/контекстное меню, установленные Windows-приложения и профили
не менялись. UI/аудиосеанс не использовался, timers/tasks не создавались.
Установленный Linux EXE и INI сохраняют прежние SHA; SDK остаётся 1.36.
