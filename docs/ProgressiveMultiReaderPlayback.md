# Progressive: несколько readers одного растущего файла

Дополнительная проверка от 3 ноября 2026 года: приложение 0.2.0,
контракт SDK 1.81. [Измерения, exit codes и SHA-256](ProgressiveMultiReaderPlaybackValidation-2026-11-03.json).
Новые исправления относятся к текущим исходникам; опубликованные SDK ZIP
и установщики этим этапом не заменяются. Harvester не изменяется.

## Проверенный сценарий

Каждая редакция проверена отдельно на четырёх RF64-профилях: PCM16/PCM24,
stereo 48 kHz, обычный и sparse hint. Два плеера открывают один физический
недокачанный файл с одним sessionId/generation. Вначале подтверждены 4 s
из 20 s, затем 12 s; оба действительно воспроизводят данные до complete.
Сверяются позиция, decoder I/O, device/fileId и неизменность исходника.
Qt дополнительно наблюдает реальные codec, rate/channels и время libmpv.

В Qt это два настоящих Window/Player с отдельными профилями и IPC endpoints
**в одном тестовом процессе**. В Classic — два независимых процесса из
отдельных временных portable-копий. Результат Qt не выдаётся за проверку
двух независимых процессов или смешанной пары Classic/Qt.

Одно воспроизведение RF64 держит две квитанции: внешнюю группу и внутренний
файловый reader. Два воспроизведения дают четыре активные квитанции;
добавленная асинхронная I/O-проверка — пятую. Три одновременные квитанции
проверяются и внутри одного профиля. На каждый профиль формата приходятся
три playback groups (включая повторное открытие) и три дополнительных
файловых readers. Всего на редакцию — 12 playback groups, 24 их квитанции
и 12 дополнительных квитанций, с уникальными readerIds.

Порядок действий проверяется в обе стороны:

- Отмена I/O-проверки закрывает только её reader; оба декодера остаются
  активными, второй продолжает двигать позицию.
- Stop первого плеера освобождает его playback group, но оставляет активными
  собственный дополнительный reader и playback другого endpoint.
- После отмены первого дополнительного reader остаётся второй плеер.
- Stop второго плеера сохраняет его дополнительный reader. Первый плеер
  снова открывает тот же файл с новым readerId и действительно воспроизводит его.
- Отмена оставшейся I/O-проверки сохраняет повторное воспроизведение.
  Только последний Stop оставляет оба реестра без активных readers.
- Файл удаляется после положительного `filesClosed` playback group,
  закрытия дополнительных readers и проверки объединения обоих реестров.

Прямой `readerRelease` по reader I/O-проверки не отменяет задачу и не даёт
ложного `released`; `readerForget` активного reader отклоняется как
`reader_in_use`. Команда release по reader другого endpoint получает
`unknown_reader` и не меняет ни одно воспроизведение.

Внутренний bridge вправе сам подтвердить и удалить свою квитанцию при закрытии.
Тест сначала требует **положительную внешнюю квитанцию группы с filesClosed**,
затем отсутствие активных её членов. Исчезновение внутренней записи само
по себе не трактуется как подтверждение освобождения файла.

| Редакция | Профили | Playback groups | Квитанций одновременно | Stop → filesClosed, max | Exit |
|---|---:|---:|---:|---:|---:|
| Linux Qt | 4 | 12 | 5 | 0.065 s | 0 |
| Windows Qt | 4 | 12 | 5 | 0.066 s | 0 |
| Windows Classic | 4 | 12 | 5 | 0.094 s | 0 |

## Исправление конкуренции при старте I/O-проверки

До исправления на Windows Qt воспроизведён `reader_registry_busy` в рабочем
потоке I/O-проверки: короткий запрос readers держал `.guard` в момент создания
новой файловой квитанции. Задача ошибочно становилась терминальной, хотя
запрошенный wait budget ещё не истёк. Ошибка и её исходный exit code 8
сохранены в отчёте.

В общем `ResourceProbeManager` raw-read loop код `reader_registry_busy`
теперь повторяется в пределах **того же уже установленного deadline**,
так же как временное ожидание файла/диапазона. Между попытками остаётся
прерываемое ожидание до 25 ms; cancel/stop прерывают его. Новый
срок после каждой попытки не создаётся. Ошибки целостности/идентичности,
reader_limit, EOF и остальные коды не маскируются. Метаданные readers
и сам ReaderLease не переводились на неограниченное ожидание блокировки.

Тест принудительно удерживает только `.guard` своего частного реестра:
проверка остаётся running, не публикует ложных readerIds и после снятия
блокировки успешно читает данные. Во время удержания отвечает capabilities.
Отдельно проверены нулевой budget, истечение 80 ms и отмена при удерживаемой
блокировке: первые два сохраняют явный `reader_registry_busy`, отмена
возвращает cancelled; во всех случаях подтверждено закрытие без readers.
Это совместимое исправление существующего API, без новых форматов или capability.

## Квитанции и интеграция загрузчика

Реестр ограничен конкретным endpoint/профилем. Ответ `readers` одного плеера
не перечисляет readers другого. Загрузчик должен хранить все endpoint и
readerIds, которым передан ресурс, и перед retire/rename/удалением учитывать
их объединение. Проверка проводится по физическим device/fileId, поскольку
внешняя группа и файловый reader могут называть один файл разными resource IDs.

`unknown_reader`, timeout и отсутствие ответа не являются разрешением на
удаление. Нужна подтверждённая квитанция своего reader/group либо уже
предусмотренное протоколом проверенное завершение процесса. Отдельный endpoint
не вправе освобождать чужой профиль. Этот этап проверяет сторону плееров
и тестового writer; реальный Harvester не подключался.

## Проверки и границы

Qt CTest: `progressive-multi-reader-playback` и
`progressive-multi-reader-regression`. Второй сохраняет прежние 11 проверок
resource-I/O API и growing AAC stereo/H.264 playback. Classic wrapper:
`tests/windows/progressive_multi_reader_playback.py` с двумя **изолированными**
копиями; тот же общий сценарий и 11 resource-I/O checks.

Linux запускается через `qt/tests/run_tests.sh` с частными X11/D-Bus/PulseAudio.
Проверяются сохранность установленных Windows EXE/INI и 158 Classic shell entries,
удаление одноразовой задачи и тестовых staging/registry directories.
Новая проверенная Linux-сборка устанавливается атомарно с backup прежнего EXE,
без изменения INI и личных файлов, без остановки текущего просмотра.

Это короткий RF64-срез, максимум пять квитанций, без writer complete/EOF.
Он не закрывает длительную нагрузку, 100 конкурентных циклов, несколько
профилей реального Harvester, смешанные пары редакций, crash/disk-full,
полную codec/container matrix и физическую A/V синхронизацию.
[Полный чеклист](ProgressiveCompletionChecklist.md) сохраняет эти пункты открытыми.
