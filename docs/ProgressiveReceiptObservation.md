# Qt: подтверждение release и повторное чтение metadata

7 ноября 2026. Проверен воспроизводимый отказ старого polling-выражения после
реального закрытия файла. Текущая проверка с сохранением положительной квитанции
и полный Window/API regression проходят на Linux Qt и Windows Qt.
[Native exits, полные логи, SHA и квитанции](ProgressiveReceiptObservationValidation-2026-11-07.json).
Production code, SDK и установленные приложения не менялись.

## Уточнение исторического отказа

В старом `windowClose:reader-release` падает выражение
`api->request(receiptQuery)["reader"].toObject()["released"].toBool()`.
Индивидуальное время этого ожидания и полный JSON ответа тогда не сохранялись.
5000 ms — настроенный параметр QTRY, а не зарегистрированное время закрытия.

Кроме того, ветка `reader-release` выполняется **до** `api.reset()` и
`window.reset()`. В этой ветке нет вызова `window.close()`. Имя общей тестовой
функции `windowClose` не делает этот отказ доказательством зависания закрытия
окна. Он остаётся неатрибутированным историческим отказом проверки receipt;
ни живой media handle, ни превышение 5 s закрытия по тому логу не доказаны.
Первоначальный отчёт и FAIL сохранены без переписывания.

## Управляемая проверка настоящего API

Новый `foxicmp-receipt-observation-tests` использует Qt Test и штатные
`ReaderLease`/`ReaderRequest`, без media backend или пользовательского профиля:

1. Создаёт и открывает настоящий файл, регистрирует его native device/file ID.
2. Закрывает media handle, сохраняет filesClosed receipt и освобождает lease.
3. Первый API ответ подтверждает `released=true`, `filesClosed=true`,
   `reason=files-closed`.
4. После этого тест захватывает только свой private `.guard`. Следующий запрос
   metadata законно возвращает `reader_registry_busy`.
5. Проверка с сохранённым proof использует уже полученную квитанцию. После
   unlock отдельно проверяет новый положительный ответ и readerForget.

Ответы API не синтезируются. Реальный файл закрыт до первой положительной
квитанции; получение busy не превращает его обратно в открытый файл.

С `FOXICMP_TEST_LEGACY_RECEIPT_ORACLE=1` выполняется прежний подход:
`QTRY_VERIFY_WITH_TIMEOUT(poll(),5000)`. QTRY вычисляет условие несколько раз.
Первая проверка получает настоящий положительный ответ, следующие — busy,
и выражение с пустым `reader` становится false. В управляемом случае это
сохраняет native exit 1 на обеих ОС. Зарегистрировано по 305 запросов,
первоначальная положительная квитанция и последний `reader_registry_busy`.
Наблюдаемый интервал всей проверки — около 15 s при параметре QTRY 5000 ms;
это дополнительно показывает, почему параметр нельзя выдавать за измеренное
время закрытия. Бюджет не увеличивался.

Без этой opt-in переменной работает текущий подход: первый положительный
ответ сохраняется вместе с flags/reason; повторная оценка QTRY не делает
новый registry запрос. Обе строки — обычная и busy-after-proof — проходят,
по одному фактическому polling-запросу. Busy status/release и восстановление
после снятия блокировки остаются обязательными проверками.

Этот способ был исправлен в тесте ещё в commit `51c7fc9d9`; новый этап добавляет
воспроизводимую регрессию для него, а не объявляет новое исправление плеера.
Управляемая инъекция доказывает возможность ложного отказа старого oracle,
но не устанавливает, какой именно ответ пришёл в историческом случае.

## Window/API и результаты

В существующий `continuousplayer_test.cpp` добавлен bounded trace: время,
число polls, первые 15 и последний ответы, сохранённый proof. Он печатается
и при успехе, и при выходе по ошибке. Условие успеха и таймаут не изменены.
Это позволит различить busy/error metadata и действительно удерживаемый reader
при следующем естественном отказе.

| Проверка | Linux Qt 6.4.2 | Windows Qt 6.12.0 |
|---|---|---|
| Текущий oracle, обычный + busy-after-proof | Native 0; Qt totals 4 PASS | Native 0; Qt totals 4 PASS |
| Старый oracle, только busy-after-proof | Native 1; ожидаемый FAIL | Native 1; ожидаемый FAIL |
| Полный настоящий Player/Window/API | Native 0; Qt totals 15 PASS | Native 0; Qt totals 15 PASS |
| Дополнительный `windowClose:reader-release` | Не запускался отдельно | Два повтора native 0; по 3 Qt PASS |

Qt totals включают init/cleanup, а не только функциональные data rows.
В основном Windows Window/API повторе четыре receipt-ветки получили proof
за 2–3 ms, по одному polling-запросу. Это измерение участка receipt observation,
не полного end-to-end закрытия. Действующие проверки удаления API/window
менее 200 ms и последующей очистки native engines также прошли.

Linux CTest exit **8** сохранён: намеренно отрицательная строка не зарегистрирована
как `WILL_FAIL`. В обычную CTest `receipt-observation` включён только текущий
oracle; отрицательный вариант запускается отдельно явной переменной.

Первый Windows wrapper завершился до записи native exit полного GUI-теста,
хотя вывод содержит 15 PASS. Причина остановки wrapper не захвачена; этот запуск
не засчитывается как завершённая приёмка. Повтор использует subprocess-обёртку,
которая записывает child returncode до возврата в PowerShell. Полный повтор и
два целевых повтора дали точные native 0.

## Сохранность и границы

Одинаковые исходники тестов собраны и проверены отдельно на обеих ОС.
Windows GUI запускался интерактивной одноразовой задачей с private profiles;
задача удалена. Linux GUI — через частные X11/D-Bus/PulseAudio `run_tests.sh`.
583 защищённых файла и 158 HKCU shell entries совпали до/после. Настройки
плееров/рабочего стола, Classic, Harvester и опубликованные assets не менялись.
Тесты не требуют новой установки Linux. Wayland и отложенное оборудование
не проверялись.

Исторический ответ Windows по-прежнему неизвестен: статус OPEN сохраняется
как неатрибутированный отказ assertion, **не как доказанная задержка закрытия**.
Полная release/latency/stress приёмка ТЗ этим не закрывается.
