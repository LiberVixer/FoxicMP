# Старт с выбранной позиции в растущем AAC-кэше

8 ноября 2026. Частные реальные Qt Player обеих ОС и Classic DirectShow graph.
Публичные API/SDK 1.84 пока сохраняют запрет seek до output complete.
[SHA, точные exits и исходные отказы](ProgressiveGrowingStartSeekValidation-2026-11-08.json).

## Проверенный сценарий

В подтверждённом, но незавершённом H.264/AAC-кэше выбирается позиция 1 s.
Qt использует новый load с `start=1`, точным seek и preroll 0,25 s; Classic —
`SetPositions` обеих проекций в уже построенном графе перед его первым Run.
После перехода проверяются вывод до writer complete, ручная пауза, публикация
оставшихся ranges, отсутствие ложного EOF и естественное завершение после
подтверждения конца. PCM и video не перекодируются, originals не меняются.

Шесть профилей включают 44,1/48 kHz, mono/stereo, fractional clocks, B16,
aligned AAC и одноотсчётную аудиодорожку перед длинным видео. В последнем
случае после 1 s аудиовывода уже нет, но видео продолжает работать.
Qt PCM сравнивается побайтно с завершёнными файловыми проекциями того же Player;
Classic PCM — с независимым сырым decoder oracle, все кадры — с NV12-хешами.

Это начальная позиция при открытии, а не повторные произвольные переходы
в играющем графе. Нельзя переносить результат в публичную capability без
следующей проверки command/reload, pause/resume, replacement, cancellation,
неподтверждённых targets и decoder-safe границ. Старые SDK/defaults не расширены.

## Найденный и исправленный отказ открытия аудио

Прежние Player-проверки обнаружили завершившийся без ошибки ролик с пустым
PCM. В журнале libmpv внешняя audio-проекция не открылась. Повтор с точной
диагностикой поймал `reader_registry_busy`: завершение producer закрывает receipts
под той же кратковременной registry guard, которую требует новый decoder reader.
Два первых отказа без точного native-кода сохраняются как исходные наблюдения;
их индивидуальная причина не объявляется доказанной задним числом.

Общий `StreamDecoderSource::decoderReader` теперь повторяет только такую ошибку
в течение 250 ms, с шагом 5 ms и проверкой отмены. Остальные ошибки не повторяются;
raw readers и IPC admission сохраняют немедленный busy. Это предел повторов,
не обещание ограничить зависший OS I/O. Открытие libmpv выполняется вне GUI.
Classic использует собственный общий reader двух проекций; его raw admission
и назначение leases не менялись ради Qt.

Qt при file-loaded дополнительно проверяет наличие обязательной AAC-дорожки.
Если она так и не открылась, Player сообщает `continuous-required-audio-unavailable`
и асинхронно останавливается. Успешное видео без обязательного звука больше
не считается корректным continuous AAC стартом. Native-код открытия пишется
в stderr, вместо потери причины за общим external-file error libmpv.

Управляемые проверки держат guard 50 ms, удерживают до истечения retry window
и отменяют открытие. Старый код с тем же fixture немедленно вернул busy вместо
успеха; исправленный проверяет release, timeout, cancel и отсутствие оставшихся
readers. Отдельный реальный Qt-тест блокирует регистрацию audio после открытия
video и требует ошибку обязательной дорожки, отсутствие natural EOF и filesClosed.

## Исправления проверок

- Первый fixture ждал 2 s общего покрытия при наличии 2 s видео и 1,92 s AAC.
  Таймаут происходил до Player load. Точные index values и исходный exit сохранены.
- После перехода на 1 s короткий исходный prefix оставлял менее секунды AAC.
  Наблюдалось ожидание без PCM; журнал file AO показывает буфер 65 536 samples.
  Контроль с четырьмя опубликованными source seconds прошёл. Для положительного
  growing-start теста используется этот запас; одних PTS ranges недостаточно для
  гарантии начала вывода. Прежние growing fixtures с трёхсекундным prefix сохранены.
- Windows file AO может не создавать файл при нулевом числе аудиоотсчётов после
  конечного AAC. Только для такого endpoint допускается отсутствующий пустой
  oracle; непустой oracle по-прежнему обязан существовать. SHA считается по bytes.
- Старый Classic seek oracle сначала декодирует весь файл, затем делает flush.
  AAC PNS state переживает flush, поэтому он не подходит для свежего старта.
  Добавлен отдельный `start-seek-raw`; прежний `seek-raw` сохранён для прежних
  completed-seek проверок. Сравнение остаётся побайтным, допуск не увеличен.

## Итог проверки и установки

- По шесть новых growing-start сценариев трёх редакций: 18, native driver exits 0.
- Прежние Player/graph сценарии: Linux Qt 31, Windows Qt 31, Classic 37; exits 0.
- GCC, ASan/UBSan, MinGW и MSVC: по 22 managed-AAC и 34 cache case, всего 224.
  В каждом наборе проверены release/timeout/cancel занятой decoder guard; exits 0.
- По одному управляемому required-audio отказу Qt каждой ОС; exits 0,
  ошибка вместо silent fallback и natural EOF, leases закрыты и cache удалён.
- Обычные Qt main EXE: по девять публичных AAC API/SDK сценариев Linux/Windows.
  Ещё девять — установленная Linux-копия с её прежним worker/SDK; exits 0.

Ещё 32 concurrent API race cases обычных Qt main EXE проверили Stop/Cancel/Release/
Publish с заменой на обычный файл, поздние события и независимый endpoint.
Один AAC-профиль stereo 48 kHz/B3/fractional; это не полная race/stress приёмка.

Это 402 конечных сценария; первые отказы и red control сохранены отдельно.
Точные дочерние exits, включая управляемый cleanup main-процессов, есть в отчёте;
нулевой driver exit не подменяет их собственные exit codes.

Linux `foxicmp-qt` заменён атомарно, версия CLI осталась 0.2.0. Прежний EXE
сохранён в backup. SHA INI до/после совпал, остальные 578 файлов установленной
папки сохранены; capabilities не изменились. Из исходных 583 защищённых файлов
изменился только этот Linux EXE; 158 HKCU shell entries совпали. Windows main Qt
проверен в частной копии с прежними pinned DLL, установленный EXE не заменялся.

Физическая A/V синхронизация, полная stress/OS I/O матрица и публичный growing seek
остаются открытыми. Harvester, Windows-установки, их настройки и release assets
не изменяются этим этапом. Проверенный Qt EXE обновляется в Linux атомарно
с backup и сохранением INI; точные результаты замены входят в JSON отчёт.
