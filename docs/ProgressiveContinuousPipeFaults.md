# Continuous remux: незавершённый pipe I/O

Проверен общий `process_detail::Process` внутри настоящего
`StreamRemuxSession`: **по 12 сценариев GCC/Linux, MinGW/Windows, MSVC/Windows и
GCC ASan/UBSan, всего 48**, exit code каждого прогона 0. Production code,
публичные capabilities, версия приложения 0.2.0 и SDK 1.82 не менялись.
[Результаты, измерения, SHA и exit codes](ProgressiveContinuousPipeFaultsValidation-2026-11-05.json).

## Доказательство точки сбоя

`tests/progressive_stream_io_crash_test.py` управляет отдельным native fixture.
Тот запускает свою дочернюю копию вместо FFmpeg, сохраняя настоящий managed
transport и ResourceSource. Приватный `childMode`/`childMarker` доступен только
в тестовом EXE; в команды плеера или worker он не добавляется. Пути передаются
через унаследованную тестовую переменную в hex, без shell. Результат рукопожатия
публикуется отдельным атомарно переименованным файлом.

Две точки проверяются без предположения, что произвольный sleep поймал нужную
инструкцию:

- **Parent receive.** Child получает настоящий SHA-проверенный блок 4096 bytes,
  затем отправляет незавершённый `io:write` с 131072 hex digits, без закрывающей
  кавычки и newline. Размер сообщения больше измеренной ёмкости pipe. Маркер
  появляется только после окончания записи: parent уже обязан был прочитать
  часть сообщения, но ещё не может обработать целую строку. Выходной файл
  остаётся пустым.
- **Parent send.** Child запрашивает 65536 подтверждённых bytes, читает только
  первые 4096 bytes JSON-ответа и больше stdin не читает. SHA принятого префикса
  сверяется с исходным файлом. Непрочитанный остаток ответа больше измеренной
  ёмкости pipe, поэтому parent не может закончить send до fault. При этом
  status остаётся доступен через отдельный поток parent fixture. У child
  отключена stdio-буферизация; префикс читается системным read/ReadFile ровно
  заданного размера, без скрытого prefetch остатка.

Ёмкость читается через Linux `F_GETPIPE_SZ` или Windows `GetNamedPipeInfo`.
Проверяется, что неравенства действительно выполнены на данной ОС; если нет,
сценарий завершается ошибкой, не объявляет блокировку доказанной.

В каждой точке выполняются смерть child, cancel и operation timeout; каждый
вариант повторяется дважды. Это 2 × 3 × 2 = 12 сценариев на сборку.

## Выход и сохранность

Перед kill сверяются executable и parent PID, удерживается OS identity того же
процесса. Linux использует pidfd/SIGKILL, Windows — проверенный process handle и
TerminateProcess(197). Cancel/timeout завершают child штатным managed teardown.
Во всех случаях ОС подтверждает его выход; parent продолжает отвечать в том же
процессе.

Смерть посреди send может вернуть `backend-pipe-error`, посреди receive —
`backend-worker-exited`: оба являются ошибкой, не EOF. Тест принимает только эти
два кода для kill, только `cancelled` для отмены и
`backend-operation-time-limit` для тайм-аута. Пустой успешный result и обработка
неполного выходного сообщения запрещены.

Проверяются filesClosed каждого source reader receipt, `reason=files-closed`,
удаление receipts, неизменность SHA оригинала/partial и возможность физически
дописать partial после release. Прочитанные bytes ограничены заданным блоком;
неопубликованный хвост не читается. У каждой RPC есть собственный timeout 2 s.

На Linux и Windows дополнительно повторены прежние parent и transport проверки,
а также настоящие public SDK worker-crash сценарии Qt. Те же четыре SDK сценария
повторены для Classic, с двумя отдельными EXE/INI и защитой регистрации до первого
запуска. 158 HKCU shell entries сверяются до/после; страница «Форматы» не открывается.
Временная одноразовая задача и тестовые Classic-копии удалены. Первый запуск
задачи указывал на отсутствовавший wrapper; его результат сохранён отдельно,
после исправления пути actual Classic test и final task exit — 0.

## Граница результата

Это детерминированный тест **транспортного компонента с синтетическим child**.
Он не доказывает смерть настоящего FFmpeg внутри конкретного file read/write,
очистку output cache/decoder в этой точке или все варианты файловой системы.
Прежние публичные worker-crash проверки подтверждают четыре внешних состояния
реального просмотра отдельно. Их сочетание не выдаётся за end-to-end mid-I/O
приёмку всех трёх редакций.

Полная crash/stress matrix, выжившие внешние readers, точные file-I/O schedules,
другие continuous codecs/containers и прежний единичный Linux heartbeat release
>2 s остаются открытыми. Новых EXE плеера нет; установленная Linux-сборка совпадает
с проверенной в предыдущем этапе. Профили, Windows-установки, SDK ZIP и Harvester
сохранены; переустановка для изменения тестов не требуется.
