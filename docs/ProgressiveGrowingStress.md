# Continuous SDK: один растущий файл и два просмотра

5 ноября 2026. Приложение 0.2.0, SDK 1.82. Это новый тест и отчёт;
production code, EXE, defaults и установленные профили не менялись.

[Первичные результаты, SHA и exit codes](ProgressiveGrowingStressValidation-2026-11-05.json).
Общая [ТЗ-приёмка](ProgressiveCompletionChecklist.md) остаётся открытой.

## Сценарий

Создаётся обычный fast-start MP4: 128 секунд H.264, 25 fps, без audio/B-frames,
3200 packets. Два независимых процесса одной редакции открывают один физический
`input.part` через разные защищённые endpoints и собственные output caches.

Изначально файл физически содержит только префикс до 12 секунд и 13 байт
следующего packet. Writer дописывает его через append-only I/O; каждой публикации
предшествует запись данных и расчёт SHA. При первом дописывании две секунды
между физической записью и публикацией подтверждают: реальный размер файла сам
по себе не разрешает чтение нового диапазона.

После нескольких публикаций writer на **60 настоящих секунд** перестаёт писать.
Heartbeat продолжает приходить раз в пять секунд. Оба decoder доходят до
доступной границы; EOF до writer complete запрещён. Первый просмотр ставится
на ручную паузу. После публикации новых данных второй продолжает играть за
прежние <2 s, первый остаётся на паузе до отдельного Play.

Затем первый просмотр закрывается с подтверждёнными filesClosed receipts и
очисткой его cache. Второй продолжает двигаться с прежними playbackId/readerIds
и тем же worker. Первый endpoint запускает новое задание с новыми identities,
используя тот же физический файл. Writer продолжает append-only публикации.

Перед complete оба просмотра ставятся на паузу. После подтверждения source
complete/producer close копии двух output caches проверяются ffprobe: payload
SHA каждого packet, нормализованные PTS, DTS и duration точно совпадают с
оригиналом. Далее seek к 126 s, Play, подтверждённый EOF, release и forget.
Оба caches удаляются только после закрытия readers; полный исходник совпадает
с исходным reference SHA.

В каждой редакции проверены два набора по 3200 packets. Это проверка copy-remux
всего файла, **не декодирование всех 128 секунд**: во время минутной остановки
был настоящий stall, затем часть видео просмотрена и выполнен seek к концу.

## Зафиксированные бюджеты

Финальные прогоны используют границы прежнего lifecycle stress:

| Показатель parent player | Порог |
|---|---:|
| Max handles/fds последних 10 samples против окна 30–40 s | +8 |
| Max threads последних 10 samples против окна 30–40 s | +2 |
| RSS/private growth против первых 10 samples | 256 MiB |
| Средний CPU последних 10 samples | ≤1 логического ядра |
| Любой измеренный SDK/reader request | <2 s |
| Возобновление второго просмотра | <2 s |
| Close + receipt check + forget | <2 s |
| Реальная продолжительность сценария | ≥120 s |

Каждую секунду сохраняются состояние обоих endpoints, физический/published
размеры и process metrics. Полные RPC durations и публикации сохраняются отдельно.
Linux fd count и Windows NT handles не сравниваются как абсолютные величины.
До запуска сценариев сохраняется SHA исходника теста. Его изменение во время
прогона вызывает отказ.

## Результаты

| Редакция | Реальное время | Пауза writer | Resume | Max request | Exit |
|---|---:|---:|---:|---:|---:|
| Linux Qt | 130,46 s | 60,09 s | 0,291 s | 0,231 s | 0 |
| Windows Qt | 129,36 s | 60,14 s | 0,235 s | 0,188 s | 0 |
| Windows Classic | 130,44 s | 60,08 s | 0,390 s | 0,187 s | 0 |

Все шесть packet comparisons дали по 3200 точных совпадений. Оба кэша одной
редакции имели одинаковые byte SHA. Linux/Windows генерируют собственные reference
через соответствующий FFmpeg/x264; равенство исходных bitstreams между ОС
не предполагается. По payload/clocks каждый output сравнивается со своим input.

Пороги handles/threads/memory/CPU и закрытия выдержаны для обоих процессов каждой
редакции. Первый Linux пробный прогон также прошёл, но предшествовал добавлению
resource assertions; его исходник и результат сохранены отдельно и не выдаются
за финальную строгую проверку. После этого один неизменный финальный SHA теста
выполнен на всех трёх редакциях.

## Воспроизведение и сохранность

CTest: `progressive-continuous-growing-stress`, label `stress`, timeout 600 s.
CLI: `tests/progressive_continuous_growing_stress.py`; каталог отчётов должен
быть новым. Classic CLI сам создаёт guarded portable copies, заранее записывает
ContextMenuPrompted=1/ContextMenuEnabled=0 и не открывает «Форматы». Для него нужны
две `--player`, runtime directory и remux worker; для Qt — один `--player`, два
приватных профиля создаёт основной harness.

Linux запускается только через `qt/tests/run_tests.sh` с частными X11/D-Bus/
PulseAudio. Windows использует отдельную одноразовую задачу, удалённую после
проверок. 17 защищённых EXE/INI/SDK/worker/PDB/LTCG файлов и 158 shell entries
совпали до/после. Harvester, MPC/MPC-BE, MPMY и системные настройки не менялись.

Нового production build нет. Установленный Linux EXE остаётся проверенной
сборкой `ebb0a806…`; повторная установка для test-only изменения не выполняется.
Исторические Linux release >2 s и Classic heartbeat-12 отказы не объявляются
объяснёнными. Многочасовая загрузка, A/V/B-frames, общий remux/форматы, stuck OS
I/O и полная stress-матрица остаются отдельными пунктами. Wayland и отложенное
оборудование не проверялись.
