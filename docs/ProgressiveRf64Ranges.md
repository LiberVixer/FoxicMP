# RF64: публикация диапазонов вне порядка

Расширение RF64 PCM16/PCM24 для параллельной локальной записи. Оно согласуется
через `standalone.rf64Pcm16.outOfOrder` / `rf64Pcm24.outOfOrder`:

```json
{
  "version": 1,
  "mode": "prefix-gated-v1",
  "maxRanges": 128,
  "maxNewBytes": 16777216,
  "playback": "confirmed-contiguous-prefix",
  "islandSeek": false
}
```

Writer может публиковать подтверждённые ranges дальше по файлу до заполнения
промежутка. Плеер принимает их и сохраняет подтверждения SHA, но индексирует
и передаёт декодеру только непрерывный префикс от нулевого байта. Размер файла,
в том числе заранее выделенного или sparse, не расширяет эту границу.
Переход в отдельный островок данных пока отклоняется обычной проверкой seek.

Например, `[0, 12 s)` и `[16 s, 20 s)` не дают 20 секунд доступного аудио.
На границе префикса остаётся buffering; отсутствующие байты не читаются как PCM
из нулей и не становятся EOF. После подтверждения `[12 s, 16 s)` ранее принятый
хвост становится частью префикса. Воспроизведение продолжается с тем же reader,
а ручная пауза сохраняется. Граница полного PCM packet может быть чуть раньше
байтовой границы. Окончательный EOF всё ещё требует writer/resource/track complete.

На начальное открытие и каждую публикацию допускается до 16 MiB **новых
подтверждённых байтов**. Заполнение одного байта может открыть для индексации
больше 16 MiB ранее опубликованных данных; оно не считается повторной
публикацией этих байтов. Все прежние диапазоны и SHA-блоки остаются неизменными.
Пределы 16 GiB, 250000 PCM packets, 128 ranges и 4096 SHA-блоков действуют вместе.
Обход лимитов через островки за объявленным ds64 extent отклоняется.
Известный размер resource должен совпадать с RF64 header.

В status RF64 добавлены точные десятичные строки:

| Поле | Смысл |
|---|---|
| `confirmedPrefixBytes` | Непрерывный подтверждённый префикс |
| `confirmedPhysicalBytes` | Сумма всех подтверждённых ranges исходного ресурса |
| `pendingOutOfOrderBytes` | Подтверждённые байты за первой дырой |
| `confirmedRangeCount` | Число ranges, целое число |

`availableSeconds` отражает только готовые полные PCM packets префикса.
`physicalReadMaxEndBytes` позволяет проверить фактические обращения к media
resource. Чтение sidecar-индекса SHA не входит в эту диагностическую величину.

SDK отказывает в отправке RF64 с разрозненными ranges старому плееру без
точной capability. Соседние ranges без дыр продолжают работать со старым
плеером. Доступны и inline SHA, и [внешние таблицы](ProgressiveExternalIntegrity.md).
При hashing appends храните inline snapshot, а externalize применяйте к копии
для передачи. Таблицы и session directory живут до filesClosed.

Это первый этап ranges playback. Произвольный seek в островки, старт без
готового head prefix, другие контейнеры, live и общая sparse-матрица остаются
отдельными пунктами [чеклиста](ProgressiveCompletionChecklist.md).


Проверенный срез SDK 1.79: [итоговый отчёт](ProgressiveRf64RangesValidation-2026-11-03.json). В нём отдельно сохранены начальные ошибки fixtures и успешные повторы. После устранения гонки индекса полный набор из 15 Qt-групп на каждой ОС прошёл с exit0; ожидание index mutex проверено без удержания mutex статуса.
