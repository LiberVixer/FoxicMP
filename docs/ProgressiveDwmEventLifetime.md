# Classic: время жизни событий DWM при повторном открытии видео

5 ноября 2026. Приложение 0.2.0, Classic 1.9.1.75, SDK 1.82.
Исправление и проверки относятся к Windows Classic. Qt-код и Harvester не меняются.

[Первичные измерения и точные exit codes](ProgressiveDwmEventLifetimeValidation-2026-11-05.json).
Предыдущие [отказы resource budgets](ProgressiveContinuousObservation.md) сохранены.

## Причина воспроизводимого роста

Отдельно скомпонованная диагностическая копия Classic воспроизвела рост
**570 → 627 handles**, предел **578**, exit **1**. После четырёх прогревочных и
100 измеряемых открытий в основном процессе сохранялись **104 Event** с адресом
создания `dwmapi.dll+0x1605d`. Два последующих прогона, с первыми восемью стеками
и без них, повторили тот же отказ. Диагностика не входит в обычный EXE.

Официальный PDB Microsoft для установленного `dwmapi.dll` **10.0.26100.1**
определил этот адрес как `CreateDxBltEvent+0xcd`. Стек первого события:

```text
CBaseSplitterOutputPin::ThreadProc → DeliverPacket
  → CMPCVideoDecFilter::Decode → CDXVA2Decoder::DeliverFrame
  → MpcVideoRenderer64.ax → d3d9.dll
  → DwmpDxGetWindowSharedSurface → UpdateDxBltEvent → CreateDxBltEvent
```

Этот же поток зарегистрировал `CDwmHwndData::WinEventCallback` через
`SetWinEventHook(EVENT_OBJECT_DESTROY, …, WINEVENT_INCONTEXT)`.
После закрытия файла поток отсутствовал (`OpenThread: ERROR_INVALID_PARAMETER`),
а события оставались. У контрольных процессов владелец обработчика был жив.
Окна renderer после закрытия не накапливались.

Windows автоматически снимает WinEvent hook при завершении зарегистрировавшего
его потока. Это описано в [UnhookWinEvent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unhookwinevent).
На этом стенде первый вывод кадра мог происходить в недолговечном splitter
thread раньше первого UI redraw; последующие окна лишались обработчика очистки
DWM. Привязка к внутренним функциям конкретной DLL используется только для
диагностики, не для production вызовов.

## Исправление

В `CMainFrame::OnFilePostOpenMedia` до `Run/Pause` вызывается штатный
`m_pCAP->Paint(true)` только для MPCVR. Renderer выводит начальный чёрный кадр
в постоянном UI-потоке. Это задаёт подходящее время жизни обработчика DWM до
доставки первого декодированного кадра.

Используется существующий интерфейс renderer. Нет вызовов недокументированных
DWM ordinal, принудительного закрытия чужих Event, переключения пользовательского
renderer или изменения драйвера/K-Lite. Повторные Play/Pause не создают новый
обязательный путь инициализации. Сохранённые INI и defaults не меняются.

## Проверки

| Исправленная копия | Циклы + warmup | Handles, max 31–40 → max 91–100 | Предел | Heartbeat expiry | Exit |
|---|---:|---:|---:|---:|---:|
| Обычный EXE без аудита | 100 +4 | 502 → 499 | 510 | 12 | 0 |
| Отдельный повтор обычного EXE | 100 +4 | 526 → 523 | 534 | 0 | 0 |
| Диагностический EXE | 100 +4 | 524 → 521 | 532 | 0 | 0 |

После диагностической серии сохраняющихся событий из `CreateDxBltEvent` **0**.
Записанные обработчики DWM принадлежат живому UI-потоку. Первый стек исправленной
копии через PDB подтверждён как `OnFilePostOpenMedia → Paint`, вызванный через
`AfxInternalPumpMessage`. Hook-журнал ограничен первыми 32 операциями; успешная
очистка всех 104 циклов подтверждается итоговым счётчиком Event, а не полнотой
этого журнала.

Обычная сборка прошла 12 настоящих paused heartbeat expiry с deadline 30000 ms.
Наибольшее наблюдаемое время от первого error до подтверждённого release —
**0,296 s**, бюджет остаётся **2 s**. Baseline и все 12 наборов resource metrics
сохранены. Отдельно прошли пять Stop/Play обычного локального файла и 16 сценариев
конкурирующих команд, включая замену воспроизведения. Их фактические exit codes —
0. В сумме проверены 300 измеряемых и 12 прогревочных циклов исправления;
это не общая приёмка всех профилей ТЗ.

Обычный проверенный EXE: SHA-256
`40f391aa3a5a2d430ed97a5ce9a88f260bb3657ca66401d916c84bd50b886665`.
В нём нет audit exports. Опубликованный SDK ZIP 1.82 содержит прежнюю сборку:
новое исправление находится в исходниках и отдельном проверенном Classic build,
не объявляется уже выпущенным бинарным обновлением SDK.

Стенд `tests/windows/progressive_event_audit.*` подключается отдельным объектом
только при ручной диагностической компоновке. Переменная `FOXICMP_EVENT_AUDIT=1`
включает process-local аудит NtCreate/Open/Duplicate/Close и WinEvent hooks;
`FOXICMP_EVENT_AUDIT_STACKS=1` дополнительно записывает первые восемь стеков
создания `DwmDxBltEvent_`. Никакого внедрения в установленный процесс нет.
Фиксированные буферы ограничивают расход памяти; collisions, неполные module
records и отсутствующие данные не считаются полной атрибуцией. Hook-журнал
хранит первые 32 операции и отдельно сообщает общее число увиденных операций.

Native self-test проверяет создание/открытие/закрытие Event, перенос через
DuplicateHandle с немедленным повторным использованием числового HANDLE,
конкурентные операции и сохранение GetLastError. Проверяются обе настройки
аудита, отдельный reader, запись стека и identity потока hook по PID/времени
создания, а не только по повторно используемому TID. Итоговые проверки прошли
с exit 0. Первый вариант fixture ошибочно запрещал повторное использование
числового HANDLE при DUPLICATE_CLOSE_SOURCE; исправлена именно эта проверка,
исходный exit 3221226505 сохранён как ошибка стенда.

Один промежуточный 100-cycle прогон прошёл budgets, но получил exit 1 при сборе
диагностики: reader был изменён во время работы и потребовал экспорт, которого
не было в том EXE. Его нельзя считать завершённой проверкой. Observer теперь
импортирует reader до сценариев и сохраняет его SHA вместе с диагностическими
исходниками. Последующие прогоны выполнялись с неизменным reader.

Raw audit buffers и дампы остаются локально в `_bin`; публикуются счётчики,
module/RVA, результаты, хеши и размеры свидетельств. Production EXE собирается
без аудита отдельной командой; используемые штатные OBJ/PCH/библиотеки, установленный
renderer и обычные выходные EXE не подменяются диагностическими файлами.

## Границы результата

Это расследование конкретного воспроизводимого роста Event. Его идентичность
старому Classic отказу после heartbeat 12 не доказана: для того случая не
сохранился baseline. Исходный Linux release >2 s также остаётся OPEN.
Video-only циклы не заменяют A/V, B-frames и полную progressive-ТЗ матрицу.
Оборудование, системный сеанс и исключённый Wayland не проверяются.

Для отдельной диагностической компоновки из актуальных обычных build outputs
в x64 Visual Studio developer prompt:

```powershell
python tests/windows/build_progressive_event_audit.py --directory _bin/event-audit-new
$env:FOXICMP_EVENT_AUDIT = '1'
$env:FOXICMP_EVENT_AUDIT_STACKS = '1'
_bin/event-audit-new/event-audit-test.exe 1
```

`--prepare-only` позволяет сначала проверить response file и команды. Каталог
должен быть новым; helper перенаправляет OUT/PDB/IMPLIB/LTCGOUT и проверяет хеши
исходных выходных файлов. Подготовка проверена на Windows с exit 0. Исследованные
EXE собирались эквивалентными приватными compile/link командами до добавления
этого helper; его полный build не выдаётся за выполненный прогон.
Не запускать полученный Classic с установленным профилем: использовать staged
копии и заранее отключённую регистрацию контекстного меню, как в основном стенде.

17 защищённых EXE/INI/SDK/worker/PDB/LTCG файлов совпали до/после. Все 158 HKCU
shell entries сохранились. Обе одноразовые тестовые задачи удалены; periodic
задач не создавалось. Установленные Windows приложения и их настройки не менялись.
Linux EXE/INI сохранены: новый Qt build не создавался, поскольку исправление
касается только Classic. Harvester, MPC/MPC-BE, MPMY и K-Lite не изменены.
