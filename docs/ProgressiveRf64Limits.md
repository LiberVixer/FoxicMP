# RF64: предельная геометрия и повторное открытие ядра

Проверка существующего SDK 1.81 и EXE 0.2.0. Общий playback-код не меняется;
новые проверки находятся в исходниках текущей ветки. Неизменяемый ZIP SDK 1.81
не перепаковывается. Итоговые данные: [отчёт](ProgressiveRf64LimitsValidation-2026-11-03.json).

Два ограничения действуют одновременно: RF64 file extent ≤16 GiB и число
виртуальных PCM packets ≤250000, по 16384 frames в полном packet. Для восьми
сочетаний PCM16/24, mono/stereo, 44.1/48 kHz тест вычисляет эффективный максимум
независимой целочисленной формулой. Для PCM24 stereo пустой допустимый JUNK
chunk позволяет получить ровно 16 GiB без нарушения PCM alignment.

Тест создаёт настоящие sparse-файлы, записывая лишь head и tail. Проверяются
полный production index, точный последний sample offset/time, PCM последнего
packet, отсутствие предварительного чтения дыры и release. Следующий PCM frame
сверх эффективного максимума отклоняется в каждом из восьми сочетаний;
неуспешное открытие не оставляет reader receipts.

В каждой ОС отдельно выполняются четыре прогревочных и 100 измеряемых циклов
native core open/status/cancel/release с чередованием максимальных PCM16/24
stereo 48 kHz. Через каждые десять циклов строится production FragmentIndex.
Из внешнего процесса снимаются RSS/private memory и число дескрипторов; в Linux
также число потоков. Linux memory: VmRSS/RssAnon; Windows: WorkingSetSize/
PrivateUsage. Эти величины не считаются одинаковыми между ОС. Проверяются
освобождение readers, время cancel+release и отсутствие нарастания ресурсов
после прогрева. Все 100 замеров сохраняются: начальный рост не исключается.
Общий допуск роста относительно первых десяти измерений — 64 MiB, наблюдаемый
live RSS — до 256 MiB. RSS/private trend сохраняется как диагностика.
Отдельная test-only команда native harness измеряет занятую и свободную кучу:
Windows HeapWalk под HeapLock, Linux mallinfo2 (`uordblks+hblkhd`, `fordblks`).
Занятые bytes после последних десяти закрытий не должны превышать максимум
первых десяти больше чем на 1 MiB. Для handles допустимы до восьми дополнительных
при начальной инициализации и не больше двух между окнами циклов 31–40 и 91–100.
Эти пределы — регрессионные допуски стенда, а не общий контракт памяти плеера.
Сведения ОС и allocator heap также не считаются взаимозаменяемыми.


Отдельный GUI/decoder сценарий проходит по два максимальных stereo 48 kHz
профиля в Linux Qt, Windows Qt и Classic. Старт с head, ручная пауза, дальний
seek в подтверждённый tail, фактическое воспроизведение возле 16 GiB, обратный
и повторный seek, ожидание неподтверждённого EOF, cancel/release. Независимый
FFmpeg сверяет PCM дальнего участка с формулой writer. Размер файла не заменяет
writer ranges; дыры остаются физически незаписанными. Файлы удаляются только
после подтверждённого освобождения.

Это не 100 полных запусков GUI/декодера и не длительный playback-тест. Файлы
максимального размера остаются недокачанными и завершаются отменой, поэтому
complete/естественный EOF на полном 16 GiB здесь не заявляются. Для меньших
физических 4 GiB файлов полный SHA и EOF проверены [отдельно](ProgressiveLargeSparseRf64.md).
Долгий CPU/cache/temp stress, несколько readers, crash, video/другие контейнеры,
остальные предельные playback rates/layouts и общая приёмка ТЗ остаются открытыми.

Воспроизведение проверяется на частных профилях. Linux запускается через
`qt/tests/run_tests.sh BUILD_DIR MEDIA_DIR -R '^progressive-rf64-limits-(native|playback)$' -V`.
Classic запускается через `tests/windows/progressive_family_test.py` с
`--rf64-limits-bits 16` или `24` и частной копией плеера. До её первого запуска:
`ContextMenuPrompted=1`, `ContextMenuEnabled=0`, проверка HKCU до/после.
Одноразовая задача и staging удаляются. Установленные EXE/INI и 158 shell keys
сравниваются по сохранённым значениям; Harvester не меняется.

Первые прогоны сохранены в отчёте. В Linux сборщик метрик ошибочно индексировал
пустые поля `/proc`; исправлен выбор только VmRSS/RssAnon/Threads. В Windows
первоначальные критерии +2 handles и 32 MiB относительно раннего окна оказались
слишком строгими для наблюдаемой инициализации: диагностическая серия показала
98→99 handles и дальнейшие 99, RSS около 9→43 MiB и последующее плато.
Промежуточный критерий только по RSS (8 MiB между более поздними окнами)
также не прошёл на Windows. Поэтому финальная проверка дополнена прямым замером
занятых/свободных heap blocks при сохранении общего предела RSS/private;
исходные серии и реальные значения не скрываются. Playback-группы обеих Qt ОС
прошли ещё внутри первых CTest с общим exit8; финальные native-only CTest
с уточнёнными проверками имеют собственные exit codes и hashes логов.

В финальном прогоне Linux busy heap изменился с 210912 до 218608 bytes,
Windows — с 279728 до 281120 bytes; свободная Windows heap в конце составляла
37551488 bytes. Это указывает на удержание свободной памяти allocator в данном
прогоне, а не накопление живых объектов источника. Наблюдаемый live RSS native
process не превышал 121 MB в Linux и 97 MB в Windows. Максимальный core
cancel+release — 0,043 s и 0,075 s соответственно. Runtime Classic cancel+release
около 0,11 s. Все итоговые проверки прошли; это ограниченный результат 100 циклов.

Методика heap measurements соответствует документации
[Microsoft HeapWalk](https://learn.microsoft.com/en-us/windows/win32/memory/enumerating-a-heap)
и [glibc mallinfo2](https://sourceware.org/glibc/manual/latest/html_node/Statistics-of-Malloc.html).
Она применяется только внутри отдельного native test process. Heap trimming,
переключение allocator или изменение рабочего сеанса не используются.
