# Progressive: переход к итоговому файлу при активном просмотре

Проверка от 3 ноября 2026 года, приложение 0.2.0, контракт SDK 1.81.
[Результаты, exit codes и SHA-256](ProgressiveFinalFileTransitionValidation-2026-11-03.json).
Проверено существующее поведение трёх редакций: новых production-исправлений
не потребовалось. Harvester, установленные EXE/INI и опубликованные assets
не изменялись.

## Проверенный порядок финализации

Два самостоятельных процесса одной редакции воспроизводят общий RF64
PCM16/PCM24 stereo 48 kHz. Чередуются обычный и sparse hint — четыре профиля
на редакцию. Вначале публикуются 4 s, затем 12 s из 20 s; оба плеера
действительно воспроизводят неполный источник, с clock и decoder I/O.

Далее тестовый writer выполняет следующий порядок:

1. Дописывает все 20 s и делает flush/fsync. Пока плееры знают только 12 s,
   вычисляет полный защищённый SHA-снимок для будущего complete.
2. Переименовывает физический файл в итоговое Unicode-имя в той же папке.
   Целевой файл до операции отсутствует. Device/inode не меняются.
3. Публикует подготовленный complete с прежним **логическим resource.name**.
   Активные readers продолжают читать закреплённые файловые дескрипторы.
4. После естественного EOF и положительного filesClosed подтверждает старые
   квитанции. Новые readers открывают уже итоговое имя через явную generation 2.

Таким образом, физические bytes и хеши готовы до rename, а complete отправляется
после rename. Это не обещание произвольного дозаписывания по новому имени
внутри прежнего поколения. Вычислять недостающие хеши по исчезнувшему старому
пути этот сценарий от SDK не требует.

| Редакция | Профили | Активных readers при rename | Естественных EOF | Открытий итогового имени | Exit драйвера |
|---|---:|---:|---:|---:|---:|
| Linux Qt | 4 | 8 | 8 | 8 | 0 |
| Windows Qt | 4 | 8 | 8 | 8 | 0 |
| Windows Classic | 4 | 8 | 8 | 8 | 0 |

## Логическое имя и подмена старого пути

Имя ресурса неизменно в пределах поколения. Попытка заменить resource.name
на итоговое имя через update получает invalid_update в обеих Qt и Classic.
Отклонённая команда не меняет readerId и не останавливает исходник; затем
корректный complete той же следующей ревизии принимается.

Дополнительно **только в тестовом каталоге** на месте старого .part создаётся
другой полноценный RF64: тот же header/длина, но другой PCM и другая file identity.
Действующие readers должны читать исходный файл, а не заново открывать старое имя.
Проверяются прежние readerId/device/fileId, отсутствие ошибки и прирост decoder I/O
после rename при чтении допубликованных 8 s.

Новая resource-I/O проверка старого пути действительно открывает подставленный
файл и получает integrity-mismatch по исходным SHA. Её filesClosed/forget
относятся только к её reader; квитанции исходных плееров остаются активными.
Это SHA-защищённый сценарий: результаты не обобщаются на снимки без integrity.

## EOF и повторное открытие

Оба плеера доходят до естественного EOF без изменения speed или искусственного
seek. Проверяются finished, release и положительная квитанция files-closed
при прежнем readerId. После этого оба API открывают завершённый ресурс с
итоговым именем и generation 2. Новые readerIds отличаются, но физический
fileId/device совпадает с исходным файлом. Подтверждаются playing и decoder I/O.

Закрытие первого нового reader сохраняет второй активным. Итоговый файл и
тестовая подмена удаляются только после подтверждённого освобождения всех
readers обоих endpoints и проверки пустых реестров поколений 1 и 2.
Два оставшихся пустых тестовых процесса затем завершаются при очистке;
их ожидаемые exit -9 Linux/1 Windows сохранены отдельно от exit 0 драйверов.

Независимый FFmpeg декодирует итоговый RF64 в PCM16/PCM24. Все bytes совпадают
с исходным сигналом: 3 840 000 или 5 760 000 байт для 20 s stereo 48 kHz.
SHA итогового файла и тестовой подмены также сверяются до удаления.
Это проверка файла независимым декодером, а не захват физического выхода плеера.

## Воспроизведение и сохранность

Общий сценарий: `tests/progressive_final_file_transition.py`.
Qt CTest — `progressive-final-file-transition`, timeout 360 s. На обеих ОС также
прошёл `progressive-resources`: 30 Linux / 28 Windows native checks, включая
побайтное чтение закреплённого ресурса после rename и подмены старого пути.
Эта native-проверка отделена от испытаний настоящих декодеров трёх редакций.

Linux запускается через `qt/tests/run_tests.sh` с частными X11/D-Bus/PulseAudio,
mute и software output. Classic использует отдельные portable-копии с
ContextMenuPrompted=1/ContextMenuEnabled=0. Сохранены production EXE/INI,
158 Classic shell entries и Harvester. Временные процессы, reader directories,
sockets/locks, одноразовая Windows-задача и staging удалены. Установленный
Linux EXE уже совпадает с проверенным: для тестов и документации замена не нужна.

## Границы

Это четыре коротких SHA-защищённых RF64-профиля на локальном fixed volume,
два отдельных процесса одной редакции. Не проверены rename больших sparse-файлов,
сегментных каталогов или внешних digest-index sidecars, межтомное перемещение,
перезапись/коллизия целевого имени, power-loss/durable directory rename и reboot.
Повторное открытие сделано через progressive API, а не через обычный CLI/ассоциацию.
Смешанные пары редакций, реальные события Harvester, полная codec/container matrix,
длительная нагрузка и физическая A/V синхронизация остаются в
[общем чеклисте](ProgressiveCompletionChecklist.md).
