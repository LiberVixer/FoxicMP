# Continuous SDK 1.82: потеря heartbeat writer

Проверяется ограниченный MP4/H.264 video-only continuous-remux через публичный
SDK и обычные endpoints Linux Qt, Windows Qt и Classic. Реальный срок heartbeat
из capabilities — **30000 ms**; тест его не сокращает и не подменяет часы.
Harvester не меняется.

## Политика ограниченного режима

Отсутствие heartbeat не подтверждает смерть процесса writer и не является EOF.
Нынешний bounded continuous-remux при превышении срока завершает именно попытку
preview с отдельным `writer-heartbeat-timeout`. Это отличается от явного
`writer-failed`, error/cancel и успешного завершения источника. Исходные файлы
не удаляются и не изменяются; ошибка preview не отменяет скачивание.

Статусные запросы не обновляют liveness writer. Неверные session/generation/writer
идентификаторы также не продлевают срок. Живой writer явно отправляет heartbeat,
включая ручную паузу просмотра и отсутствие новых байтов. Валидная публикация
новых ranges тоже продлевает срок. Завершённый writer/resource больше не требует
heartbeat: завершённый output можно держать на паузе и затем досмотреть.

Поздний heartbeat/update закрытой попытки получает `continuous-closed` и не
восстанавливает старый playback. После реальных close/forget живой writer может
явно создать новый `ContinuousRemux`, подготовить те же bytes и отдельно вызвать
Play. Подготовка новой попытки не запускает её автоматически. Автоматическое
восстановление позиции/паузы после разрыва и полный reconnect-сценарий ТЗ этим
ограниченным результатом не объявляются завершёнными.

## Исправление paused decoder Qt

Исходный прогон обнаружил одинаковый отказ обеих Qt ОС: после heartbeat timeout
на ручной паузе producer/worker прекращали работу, а mpv продолжал удерживать
output reader. Пауза не заставляла декодер сделать ещё одно чтение и заметить
ошибку. Проверка release за 2 s падала; явный SDK close освобождал файлы при
очистке теста. Classic прошёл тот же сценарий без изменения программы.

Qt Window теперь проверяет read-only error observer своего continuous producer
на **существующем 100 ms GUI tick**. При ошибке он однократно отсоединяет свой
decoder, сохраняет ошибку и показывает её пользователю. Это не зависит от
вызова playback status клиентом и не имитирует heartbeat от имени writer.
Observer очищается при закрытии/замене источника, поэтому поздняя ошибка прежнего
preview не останавливает другое воспроизведение. Новые таймеры не создаются.

## Воспроизводимые проверки

`tests/progressive_continuous_heartbeat_conformance.py`, Qt CTest
`progressive-continuous-sdk-heartbeat`, timeout 420 s.
[SHA-256, результаты и точные exit codes](ProgressiveContinuousHeartbeatValidation-2026-11-04.json).

Пять сценариев каждой редакции:

1. Неполная инициализация с подтверждёнными четырьмя байтами. Запросы status и
   heartbeat от чужой generation не предотвращают истечение срока.
2. Настоящий просмотр до complete, затем отсутствие heartbeat. Нет ложного EOF;
   поздние writer events отклоняются. Новая явная попытка открывает тот же оригинал.
3. Настоящий просмотр переводится на ручную паузу. После timeout выходные readers
   и cache освобождаются и без команды Stop от клиента.
4. Валидный heartbeat примерно на 20 s и публикация нового префикса примерно
   на 40 s сохраняют попытку за прежними дедлайнами. Отказ возникает только
   через 30 s после последнего продления.
5. Подтверждённый завершённый источник играет, затем больше 32 s держится на паузе
   вообще без heartbeat. Ошибки нет; seek и подтверждённый EOF остаются доступными.

До timeout каждый status проверяется на отсутствие `outputComplete/sourceComplete`
и ложного `finished`; завершение фиксируется в интервале 29,9–32 s от последнего
валидного продления. Затем проверяются закрытие source/output и положительные
`filesClosed` receipts. Отдельный endpoint с heartbeat сохраняет свою подготовку.
SHA-256 оригинала сохраняется, поздние команды не запускают просмотр вновь.

Фактический выход worker доказывается удерживаемым Windows process handle либо
Linux pidfd, а не отсутствием процесса с данным PID при разовом опросе. Код выхода
Windows worker при управляемом прерывании сохраняется отдельно от кода теста;
он не выдаётся за нормальный EOF. Исходные Qt отказы сохраняются в отчёте.

Дополнительный настоящий Qt Window/API тест `producer-error-paused` публикует
ошибку producer при паузе и ждёт нулевого числа output readers **без playback
status/control/readerRelease**. Он также проверяет error/reason и настоящий label.
Обычные replacement/release, SDK и buffering сценарии повторяются на исправленных
Qt-сборках. Тестовые idle-процессы завершаются отдельно от приёмки crash/shutdown.

Граница результата: локальный bounded VOD профиль. Настоящее падение writer,
перезапуск player/worker, near-deadline races, восстановление прежней позиции,
все контейнеры, длительный stress, audio/AAC trim и B-frames остаются отдельными
этапами. Дисковые меню, физическое оборудование и Wayland не проверяются.

## Открытое замечание по задержке Linux

Первый полный прогон исправленной Linux-сборки завершился с **CTest exit 8**:
два отказа из 12 групп. Waiting-тест преждевременно требовал decoder reader при
открытии; его исправили, дополнительно восстановили heartbeat независимой
контрольной сессии. Итоговые waiting-прогоны обеих Qt ОС: по пять PASS, exit 0.
Второй отказ — освобождение source/cache после heartbeat timeout на паузе заняло
больше двух секунд. Причина этого единичного превышения пока не установлена.
Последующий неизменённый по успешному пути heartbeat-тест прошёл все пять
сценариев Linux, exit 0; диагностический повтор также прошёл. Windows Qt прошёл
12 групп, exit 0; Classic — пять heartbeat-сценариев, exit 0.

Эти успешные повторы **не закрывают** воспроизводимость двухсекундного бюджета.
Следующий шаг — локализовать задержку автоматического release в Linux, затем
shutdown/crash и длительная stress matrix. В тест добавлен сбор producer/playback/
reader diagnostics только при отказе, без ослабления порогов. Windows/Classic
проверены предыдущим вариантом того же теста: разница только в этом блоке
диагностики исключения; SHA каждого реально выполненного варианта сохранён.
