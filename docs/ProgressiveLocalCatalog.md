# Локальное чтение страниц каталога — подготовительный этап

На 30 октября 2026 реализован `shared/progressivelocalcatalog.h`:
`LocalSegmentCatalog` читает страницы [внутреннего каталога](ProgressiveSegmentCatalog.md).
Это файловый адаптер модели, **без подключения к playback и публичному SDK 1.36**.
Harvester, установленные приложения и их настройки не меняются.

## Чтение и идентичность

Адаптер переиспользует проверенное локальное открытие `ResourceSource`:
закрепляет принадлежащую пользователю папку, запрещает ссылки/reparse points,
hard links, неподходящий тип файла и поддерживаемые адаптером сетевые/FUSE тома.
На Windows допускается также default owner текущего токена по прежним правилам
ResourceSource. Имена страниц проходят проверку до обращения к диску.

Читается одна страница за раз. Её физическая длина проверяется **до выделения
буфера и чтения**, должна точно совпадать с дескриптором и быть не больше 64 KiB.
Чтение разбито на блоки не больше 4096 байт. После чтения повторно проверяются
длина, идентичность файла и закреплённая папка. Дескриптор страницы закрывается
до возврата байтов декодеру; декодер независимо проверяет SHA-256 и модель.

Для принятых страниц сохраняются volume/device + file ID. При обновлении
повторное открытие обязано вернуть тот же файл, даже если подмена содержит
побайтно такой же JSON. Изменение содержимого в том же файле обнаруживается по
SHA-256. Привязки новых страниц и новая модель принимаются только после проверки
всех страниц и `AdvanceSegmentCatalog`; отклонённый update их не меняет.

| Ситуация | Результат |
|---|---|
| Новая страница ещё не появилась | `waiting-index`, прежняя модель сохранена |
| Уже принятая страница исчезла | `missing-index`, не ожидание и не EOF |
| Файл страницы заменён | `source-replaced` |
| Байты не совпадают с SHA-256 | `integrity-mismatch` |
| Физическая длина не совпадает | `catalog_length_mismatch` |
| Неполное чтение после проверки длины | `source-truncated` |
| Отмена замечена до принятия модели | `cancelled`, прежняя модель сохранена |

Папка вместо файла отвергается на обеих ОС. Windows может отказать уже в
`CreateFile` с `resource-io-error`; Linux открывает объект и отклоняет его тип
с `unsafe-resource`. Эти результаты не маскируются общим успешным ответом.

## Владение и отмена

`publish()` и `catalog()` последовательно вызывает владелец в worker;
только `cancel()` допускает конкурентный вызов. Сам класс не создаёт потоки,
таймеры или UI-задачи. При подключении к движкам подготовку по-прежнему нужно
разместить вне UI и обеспечить сериализацию владельца.

Отмена проверяется до/после открытия, между блоками чтения, между страницами
и перед принятием модели. Windows overlapped-read использует прежнюю отмену
`ReadAt`; Linux проверяет флаг вокруг `pread`. Это кооперативная отмена,
**не гарантия прерывания зависшего системного вызова открытия/чтения** и не
отмена посередине парсинга JSON. После `cancel()` нужен новый объект адаптера.

Адаптер удерживает папку, но не хранит открытые файлы страниц после чтения.
Метаданные привязок ограничены числом страниц — 128. Reader leases страницам
не выдаются: после чтения остаётся копия проверенного JSON, не файловый reader.
Writer должен сохранять опубликованные страницы для последующих обновлений
и повторного открытия сессии. Плеер не удаляет страницы или медиа.

## Проверено и что дальше

[Проверка файлового слоя](ProgressiveLocalCatalogValidation-2026-10-30.md):
25 сценариев Linux и 24 на Windows с MinGW и MSVC, без пропусков;
FIFO отдельно проверен только на Linux. Проверены каталог на 8192 ресурса,
подмены/ссылки, отмена, повторное чтение и отсутствие роста числа handles.

Следующий этап — ограничение **медиа**-handles и reader leases с проверкой
повторно открываемых ресурсов, затем подключение каталога к общему bridge,
Qt/Classic и согласование публичного SDK. Лимит 64 ресурсов действующего
playback этим изменением ещё не снят. Настоящие длинные A/V-тесты, перемотка
и release больших каталогов остаются обязательными.
