# Подготовка progressive-источника вне UI

SDK 1.7, Linux Qt, Windows Qt и Classic. Совместимая JSON-оболочка версии 1,
прежние команды и медиапрофили v1/v2. YouTubeHarvester не изменяется.

## Что изменилось

Вызовы `probe`/`start` через IPC проходят три стадии:

1. В потоке интерфейса проверяются JSON, поля, состояние текущего просмотра и
   допустимость замены. Эти операции ограничены размером запроса 65536 байтов.
2. В рабочем потоке открываются локальные ресурсы, читаются init/index,
   строятся MP4-индексы и создаются необходимые reader leases. Probe закрывает
   все свои файлы в рабочем потоке и не создаёт активного просмотра.
3. Интерфейс повторно проверяет состояние и подключает подготовленный источник
   к окну/медиадвижку. Тяжёлое открытие не повторяется на этой стадии.

Wire-клиент продолжает ждать обычный конечный JSON-ответ. Новый job API или иной
IPC endpoint не нужен. Старые Python-клиенты и V2PreviewSession совместимы.
В capabilities появился отдельный объект:

```json
{
  "mediaPreparation": {
    "offUi": ["probe", "start"],
    "maxConcurrent": 1,
    "responseDeadlineMilliseconds": 5000,
    "updatesOffUi": false,
    "cancellableDiskIo": false
  }
}
```

На один API-профиль допускается одна подготовка. Qt обслуживает capabilities и
другие быстрые команды во время неё; второй probe/start получает
`preparation_busy`. Classic сохраняет один последовательный pipe-клиент:
второй RPC ждёт освобождения соединения, но окно продолжает обрабатывать сообщения.
После таймаута незавершённая подготовка сохраняет свой слот до окончания работы;
новая подготовка не создаёт неограниченную очередь работников.

«Стоп», «Закрыть», запрос открытия другого источника и закрытие API отменяют
применение запоздавшего результата. В Classic Stop/Close доступны уже во время
подготовки, даже когда фильм ещё не открыт. Завершение фоновой операции не может
возобновить отменённый просмотр. При изменении намерения воспроизведения запрос
получает `preparation_cancelled`. Qt также отклоняет применение после disconnect;
Classic проверяет доступность pipe перед отправкой результата на UI.
Потерю соединения непосредственно во время финального commit исключить нельзя:
при потерянном ответе всегда использовать reader recovery.

Ошибки `preparation_busy`, `preparation_cancelled`, `preparation_timeout` (Classic)
и `preparation_unavailable` означают соответственно занятый слот, отменённое
намерение просмотра, превышение серверного ожидания и невозможность создать worker.
В Qt истечение 5 секунд закрывает соединение. Клиентский TimeoutError не является
подтверждением отсутствия читателя; сохранять файлы и опрашивать
`readers(sessionId,generation)` / readerStatus / readerRelease.

## Границы этого этапа

Это перенос **первичного открытия и индексации через IPC**, а не всего I/O плеера.
Прямой внутренний C++ `request()`/Handle без контекста подготовки сохраняет
синхронный режим для совместимости существующих внутренних вызовов и тестов.
Legacy/provider, update/complete и последующая индексация, фоновые проверки
файлов, их общие mutex и некоторые status/close-пути требуют отдельного расширения.
Поэтому пункт ТЗ «ни одно ожидание I/O не блокирует UI» ещё не закрыт полностью.

Native filesystem read/open нельзя безопасно принудительно прервать этим
изменением. Worker не удерживает окно/API и при их закрытии не присоединяется
к UI-потоку; незавершённая операция сохраняет свои владения до фактического
окончания. Это не гарантия закрытия любых OS handles за две секунды.
Не объявлять released до положительной OS-квитанции. Неиспользованный кандидат
закрывается вне UI; при потерянном ответе может остаться подтверждённая закрытая
квитанция, которую загрузчик должен обнаружить и acknowledge.

Обычные UI-страницы, тема, профиль и значения по умолчанию не менялись.
Медиаматрица прежняя: v1 MP4/M4A и [ограниченный v2 fMP4 H.264/AAC-LC](ProgressiveMediaV2.md).
Физический A/V sync, live и новые кодеки этим этапом не добавляются.
