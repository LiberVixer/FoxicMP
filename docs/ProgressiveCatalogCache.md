# Ограниченный медиа-кэш большого каталога

Режим `ResourceSource(..., ResourceMode::BoundedCatalog)` подключён к
[playback SDK 1.37](ProgressiveCatalogPlayback.md) трёх редакций. Прежние
inline-сессии SDK 1.36 остаются совместимыми. Harvester и профили не меняются.

## Пределы и совместимость

Режим получает уже раскрытый JSON из [локального каталога](ProgressiveLocalCatalog.md).
Повторный внутренний parser проверяет до 8192 ресурсов. Одновременно открыто
не более **восьми медиафайлов**. Это предел media HANDLE/fd, а не всех handles
процесса: отдельно существуют папка, квитанции читателей и краткоживущие объекты I/O.
Из кэша вытесняется наименее недавно использованный ресурс; запрос открытого
ресурса переносит его в конец очереди.

Известная длина и конец подтверждённых диапазонов одного ресурса ограничены
16 MiB, в том числе при неизвестной полной длине. Необъявленные физические байты
за этими пределами не читаются. `retired` не допускается: модель
retirement/live и удаление опубликованных ресурсов остаются другой задачей.
Неполные ресурсы сохраняют обычные подтверждённые ranges; решение, когда целый
сегмент можно передать движку, остаётся у segment layout/bridge.

`ResourceMode::Inline` остаётся режимом по умолчанию с прежними пределами и
закреплением всех прочитанных файлов до освобождения владельца. Он не начинает
автоматически вытеснять файлы или требовать SHA-256. Новый режим выбирается
bridge только для сессий с `segmentCatalog`; отдельной публичной команды
`openCatalog` нет — она существует только в native test fixture.

## Повторное открытие и SHA-256

Для каждого посещённого ресурса сохраняется идентичность device/volume + file ID.
После вытеснения новый файл по тому же имени отвергается как `source-replaced`,
даже если байты совпали. Повторное использование одного физического файла
другим ресурсом также отвергается. История ограничена числом ресурсов сессии.

**Все ресурсы нового режима обязаны иметь `resources[].integrity` SHA-256**,
покрывающий подтверждённые байты. Без него возвращается `integrity-required`.
Одной идентичности файла недостаточно: ОС может повторно использовать номер
закрытого файла; содержимое может быть переписано без смены номера.

При повторном открытии создаётся новый `Pin`; прежний verified-block cache
не переносится. Затронутый integrity block проверяется до возврата первого его
байта, затем переиспользуются прежние проверки подтверждённых диапазонов и
кэшированных chunks. Подмена содержимого, truncation и исчезновение полного
ресурса остаются ошибками, а не EOF/ожиданием. Ошибка required-ресурса сохраняется.

`verifyPinned()` проверяет только восемь текущих pins. Закрытые ресурсы проверяются
при следующем обращении; фонового полного сканирования истории нет. Успешный
read доказывает проверку затронутых блоков, а не всех байтов ролика сразу.

## Порядок закрытия и reader leases

При вытеснении используется существующий `Pin`:

1. Фактически закрывается медиа HANDLE/fd.
2. `filesClosed` записывается в квитанцию; закрывается её lock/handle.
3. Под `.guard` проверяется `released`, только затем забывается собственная
   квитанция закрытого reader. Уже забытая другим владельцем квитанция допустима.
4. Только после этого открывается следующий ресурс и создаётся новая lease.

Неопределённое состояние/ошибка acknowledgement не разрешает открывать всё новые
файлы. Незавершённая квитанция сохраняется для консервативного завершения;
чужие квитанции не удаляются. Повторное открытие ресурса получает новый reader ID.
Поэтому 200 последовательных ресурсов не исчерпывают лимит registry в 128 записей.

Методы читают байты в принадлежащий вызову буфер; наружу не передаётся заимствованный
медиа HANDLE. Mutex `ResourceSource` сериализует чтение/вытеснение/публикацию.
Последние восемь pins остаются живыми, пока существует хотя бы один владелец source.
Последний владелец закрывает их перед итоговыми release receipts. Закрытые
финальные квитанции по-прежнему можно явно подтвердить/забыть обычным reader API.

Отсутствие активной **resource**-lease не разрешает writer удалить опубликованный
non-retired сегмент: к нему ещё возможна перемотка. При будущей интеграции нужен
lease всей playback-сессии и сохранение файлов до её подтверждённого завершения.
Этот контракт должен быть согласован через новую capability, а не предполагаться
для существующего Harvester.

Число файлов ограничено; время ожидания диска/registry этим не ограничивается.
В частности, прежний `filesClosed()` может ждать `.guard`, а Linux `pread` не
становится прерываемым syscall. Подготовка/retirement должны выполняться вне UI.

## Проверка и следующий шаг

[Отчёт](ProgressiveCatalogCacheValidation-2026-10-30.md): одинаковые 15 native
сценариев GCC, MinGW и MSVC; 200 последовательных файлов, стабильные OS handles,
восемь leases, возврат к старым ресурсам, 8192 metadata-записи, подмены, публикация,
отмена и последний владелец. Прежний inline-режим отдельно сохраняет 16 pins.

Подключение к `Fmp4V2Bridge`, Qt/Classic и SDK negotiation выполнено в SDK 1.37;
проверены 90-секундные записи с seek, паузой, обновлениями, перезапуском и release.
Многочасовая приёмка, реальные загрузчики и точные длительные A/V-измерения
остаются следующими этапами. Для прежнего inline-формата предел 64 сохраняется.
