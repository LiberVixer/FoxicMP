# Внутренний MPEG-TS ResourceSource и виртуальный поток

`shared/progressivetsstream.h` соединяет существующие ResourceSource, локальный
каталог и [AVC/AAC clock/index](ProgressiveTsAccessIndex.md). Это общий C++17
компонент для будущих Classic и двух Qt-адаптеров. Он проверялся отдельно до подключения к плеерам; результаты этого внутреннего
этапа сохранены в отчёте ниже. SDK 1.39 подключает его через
[виртуальный fMP4 адаптер трёх редакций](ProgressiveTsPlayback.md).

## Профиль и подтверждение ресурсов

Принимаются две обязательные отдельные дорожки `video`/`audio`,
`containerHint: "mpegts"`, H.264 и AAC-LC с ограничениями codec/index профиля.
Нужны известная длительность VOD, timebase 1/10000000 и постоянный общий
`timeline.timestampOffset`, равный точному пересчёту исходного 33-bit 90 kHz
clock. Этот origin вычитается из PTS/DTS, сохраняя B-frame preroll.

У каждой дорожки отдельный внешний PAT/PMT init и последовательные media
ресурсы. Нельзя менять конфигурацию/init, пропускать sequence, перебазировать
сегменты, добавлять discontinuity, muxed A/V или live. Сохраняются limits:
1 MiB init, 16 MiB media, 4 MiB PES, 65536 access units на сегмент и пределы
общего индекса. Эти пределы не являются свидетельством многочасового теста.

SHA-256 обязателен для каждого ресурса, включая inline manifest. ResourceSource
всегда использует bounded cache: до восьми одновременно открытых media/init
файлов, повторная проверка file identity и integrity при открытии вытесненного
ресурса. Поддерживаются inline snapshots и существующий `segmentCatalog`.
Это внутреннее применение каталога, а не новая опубликованная negotiation
capability. Режим каталога нельзя менять внутри сессии.

## Readiness, чтение и публикация

Виртуальный byte layout каждой дорожки — `init + media1 + media2 + ...`.
В него входит только непрерывный префикс полностью готовых, подтверждённых
ресурсов. Наличие более позднего файла на диске не позволяет перескочить дыру.
PAT/PMT, codec/config, envelope и clock новых сегментов проверяются до публикации
нового layout и индекса. Индексы опубликованных состояний неизменяемы; status
читает их без дискового I/O. `publish` сериализован и предназначен для worker,
поскольку выполняет I/O, SHA и разбор сегментов. Увеличение префикса копирует
прежний индекс; большой полностью готовый старт и частые большие обновления
требуют отдельной оценки стоимости.

Byte read ограничен 64 KiB. Чтение через границу ресурсов использует временный
буфер: при ошибке вызывающий код получает ноль байтов и неизменённый буфер.
`sample` собирает AVC Annex B или AAC ADTS/raw payload по проверенным TS/PES
диапазонам. Внутри используется окно 64 KiB, чтобы не перечитывать SHA-блок
для каждого 184-byte payload. Размер результата ограничен размером PES.
Seek использует общий IDR/audio index. Конец готового префикса возвращает
ожидание; EOF появляется лишь после полного состояния самой дорожки и всех
её сегментов. Общая готовность ограничена обеими дорожками и duration.

Ошибки до изменения ResourceSource — неверный manifest/profile/Advance или
ещё не записанная страница каталога — сохраняют прежнее читаемое состояние.
Такой кандидат можно исправить и повторить. После `ResourceSource::publish`
ошибка I/O/integrity/codec не откатывает внутреннюю модель источника: сессия
переходит в постоянную ошибку, дальнейшие read/sample не отдают байты. Для
повторного открытия нужен новый stream. Status сохраняет прежнюю принятую
revision/индекс для диагностики, но readiness обнуляется. Это намеренно
консервативная семантика, а не обещание транзакционного отката всех I/O.

Отмена проверяется между ограниченными чтениями и после разбора; это не
жёсткий deadline для системного I/O или CPU. Файлы и reader leases принадлежат
общему владельцу stream. После последнего владельца сначала закрываются
дескрипторы, затем удаляются закрытые квитанции; при сбое registry остаётся
консервативная запись для recovery. `releaseReceipt` подтверждает закрытие
ResourceSource, а не просто команду закрытия UI.

## Проверка и следующий этап

Нативный стенд `tests/progressive_ts_stream_cli.cpp` не является API плеера.
Python conformance проверяет дыру/добавление/ожидание/EOF, backward bytes и
samples, большой PES, ошибки кандидатов, замену/перезапись/усечение вытесненного
файла, отмену, last-owner cleanup и 242 ресурса в семи страницах каталога.

Два реальных FFmpeg-профиля проверяют Main с B-кадрами + AAC 48 kHz и High
29.97 fps + AAC 44.1 kHz. Сверяются все 438 encoded packet hashes, PTS/DTS и
байты виртуального потока. Собранные elementary потоки декодируются внешним
FFmpeg: hashes video и PCM совпадают с исходными TS. Это проверка пути
ResourceSource → sample gather → FFmpeg; декодеры установленных приложений,
физическая A/V sync и реальные YouTube/Rutube/VK этим не проверяются.

[Точные результаты компиляторов и exit codes](ProgressiveTsResourceStreamValidation-2026-10-30.md).
Далее — подключение bridge/engine adapters трёх редакций, buffer/seek/update/
complete/release с настоящими декодерами и лишь затем capability и новый SDK.
Harvester и пользовательские установки в этом внутреннем этапе не меняются.
