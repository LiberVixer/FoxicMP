# Внешний индекс SHA-256 для RF64

Расширение schema 2, согласуемое через
`capabilities.schema2Playback.integrity.externalIndex`. Нужны `version: 1`,
`format: "sha256-blocks-le-v1"` и соответствующий container в
`playbackContainers`. Пока это только `rf64-pcm16` и `rf64-pcm24`.
Старый inline `integrity.blocks` продолжает работать. Переключать inline/external
внутри одной generation нельзя; при необходимости источник открывают заново.

Вместо массива блоков ресурс передаёт:

```json
"integrity": {
  "algorithm": "sha256",
  "index": {
    "format": "sha256-blocks-le-v1",
    "name": "integrity-<sha256>.idx",
    "bytes": "45320",
    "sha256": "<64 lowercase hex digits>"
  }
}
```

`name` — обычное относительное имя файла внутри session directory. Каталоги,
ссылки/reparse points, hardlinks и совпадение с именем media resource запрещены.
`bytes` — каноническая десятичная строка; точная длина файла, кратная 44,
не более 180224 байт. Пустой индекс допустим при отсутствии confirmed ranges.

Каждая запись занимает ровно 44 байта без заголовка:

| Смещение | Длина | Значение |
|---|---|---|
| 0 | 8 | unsigned offset, little endian |
| 8 | 4 | unsigned length, little endian |
| 12 | 32 | бинарный SHA-256 блока media resource |

Не более 4096 записей; длина блока 1–4194304 байта. Прежние правила точного
покрытия confirmed ranges, отсутствия пересечений и неизменности опубликованных
блоков сохраняются. Предел JSON-команды 64 KiB не увеличивается. Большой индекс
не проходит через JSON-массивы с их отдельным ограничением числа элементов.
Для больших файлов используйте `protect_snapshot(..., block_bytes=4194304)`:
обычный default 256 KiB исчерпает 4096 записей намного раньше. Неполные блоки
ранних публикаций также расходуют записи и остаются неизменными. Ограничения
числа записей, размера файла и числа PCM packets действуют одновременно.

Metadata-only validation проверяет ссылку и форму snapshot без доступа к ФС.
При открытии/публикации ResourceSource открывает индекс защищённым local I/O,
проверяет точную длину, SHA всего файла и все записи до передачи snapshot
декодеру. Принятые записи копируются в память; последующее изменение sidecar
не меняет принятые digests. Сами media bytes проверяются по SHA при чтении.
Это не предварительное хеширование всего фильма самим плеером.

SDK `externalize_integrity(snapshot, directory)` создаёт immutable файл с
content-addressed именем, flush/fsync и без перезаписи существующего файла.
Храните исходный inline snapshot для следующего `protect_snapshot(previous=...)`;
externalize вызывайте только для копии, отправляемой плееру. Старые sidecars
нужно сохранять до `reader.filesClosed`: асинхронное открытие ещё может обращаться
к ссылке из ранее отправленной ревизии. После закрытия удаляет их владелец сессии.

Функция не меняет YouTubeHarvester, сетевые загрузки, media-файлы или их формат.
Старый плеер без capability получает отказ SDK до отправки indexed snapshot.
