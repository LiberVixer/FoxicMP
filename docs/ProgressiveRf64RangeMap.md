# RF64: диагностическая карта полных PCM-пакетов

Следующий компонент после [prefix-gated ranges](ProgressiveRf64Ranges.md).
Карта описывает геометрию целиком подтверждённых PCM-пакетов в том числе за
дырами. Она не разрешает decoder seek в островки и не доказывает корректность
или фактическое декодирование их содержимого.

Каждая RF64 capability `standalone.rf64Pcm16` / `rf64Pcm24` содержит `rangeMap`:

```json
{
  "version": 1,
  "field": "rf64RangeMap",
  "geometryOnly": true,
  "payloadVerified": false,
  "islandSeek": false,
  "maxIntervals": 32,
  "timebaseDenominator": 10000000
}
```

В активном status поле `rf64RangeMap` содержит `version`, `geometryOnly`,
`payloadVerified`, `islandSeek`, `sampleRate`, `packetFrames` (16384),
`intervalCount`, `truncated` и `intervals`. Последняя закрывающая квитанция
Classic может не содержать активные media diagnostics; проверяйте наличие поля.

Каждый интервал задаётся шестью каноническими десятичными строками и флагом:

| Поле | Значение |
|---|---|
| `firstFrame` | Первый PCM frame включительно, от начала data |
| `endFrame` | Последний PCM frame исключительно |
| `offset` | Физическое начало в исходном RF64 resource |
| `length` | Число исходных PCM-байтов |
| `startTicks` | Начало в единицах 1/10000000 секунды |
| `endTicks` | Конец в единицах 1/10000000 секунды |
| `prefix` | Весь интервал находится в непрерывном head prefix |

PCM frame — один sample каждого канала. Для PCM16 stereo это 4 байта,
для PCM24 stereo — 6. Пакеты привязаны к началу RF64 data, а не файла.
Соседние ranges сначала объединяются: граница публикаций может проходить
внутри sample или packet. Затем начало округляется вперёд до начала пакета,
конец — назад до его конца. Короткий последний пакет включается, только если
подтверждены все его PCM-байты; RIFF pad в него не входит.

Intervals отсортированы, не пересекаются и не проходят через дыру. В ответ
попадают первые 32. `intervalCount` сообщает общее число до усечения,
`truncated` — наличие остальных. Не считайте отсутствие интервала доказательством
недоступности хвоста при `truncated: true`. Сами ranges по-прежнему ограничены 128.

Расчёт использует уже принятые writer ranges и проверенный RF64 header, без
чтения media или digest-sidecar. Поэтому `payloadVerified: false`: опубликованный
SHA будет проверен при фактическом чтении. Даже если данные раньше читались,
эта карта не служит сертификатом их текущей целостности.

`availableSeconds`, decoder-visible bytes, буферизация, ручная пауза и границы
seek остаются прежними: только непрерывный префикс. Наличие островка на карте
не означает, что его можно воспроизвести. Для этого ещё нужны стабильная
виртуальная раскладка через holes, оба decoder adapters, ожидание на конце
островка и отдельная сквозная проверка.

Нативные тесты используют побайтовые/пакетные независимые oracle, partial samples,
adjacent ranges, один отсутствующий байт, короткий конец и 65 интервалов.
Отдельный синтетический тест проверяет 64-bit адреса за 4 GiB без создания
физического большого файла. Реальные status проверяются в growing playback
Linux Qt, Windows Qt и Classic, включая заполнение дыр и отказ island seek.


Проверенный срез SDK 1.80: [отчёт от 3 ноября](ProgressiveRf64RangeMapValidation-2026-11-03.json), по 242 native checks и 1608 synthetic geometry cases на ОС, фактические status/playback четырёх profiles каждой редакции. Все итоговые exit codes 0; island seek не объявлен.
