# Физические RF64 больше 4 GiB

Новый сценарий `tests/progressive_rf64_large_playback.py` дополняет
[синтетические RF64-проверки SDK 1.77](ProgressiveRf64.md). Итоговые результаты
зафиксированы в [отчёте от 3 ноября 2026](ProgressiveLargeRf64Validation-2026-11-03.json): по два физических профиля в каждой из трёх редакций, все итоговые exit codes 0.

Для PCM16 и PCM24 stereo 48 kHz тест записывает обычный файл размером
4 GiB + 8 MiB + RF64 header. Все байты последовательно записаны; sparse-файл,
один лишь truncate или подмена физического I/O не используются. Временные
данные удаляются после закрытия readers. Нужен запас свободного места 12 GiB.

Через публичный API проверяются начальная буферизация, старт с 12-секундным
prefix, ручная пауза, публикация всего физического файла порциями до 16 MiB
при состоянии downloading, переход за 4 GiB, продолжение, writer complete,
переход к концу, естественный EOF, released/filesClosed и удаление receipts.
Каждая команда остаётся в лимите 64 KiB; SHA публикуются внешними индексами.

`physicalReadMaxEndBytes` — диагностическая десятичная строка в status raw-audio:
максимальный конец реально успешного чтения media resource после проверки SHA.
Чтение файла digest-индекса в неё не входит. Дальний переход засчитывается
только вместе с настоящим clock/codec/playing декодера и чтением за 2^32.
Отдельный FFmpeg декодирует полсекунды с той же дальней позиции и сравнивает
PCM с независимой формулой writer. Период 4093 frames позволяет отличить
переполнение 32-bit offset от правильных данных. Полный SHA физического файла
после playback сравнивается с SHA всех последовательно записанных байтов.

Первый физический прогон выявил в Qt последовательное сканирование MOV при
дальнем seek. RF64-адаптер Qt теперь использует проверенный FragmentIndex:
каждый новый stream reader видит исходный initialization, затем moof/mdat
от выбранного PCM packet. Это только отображение виртуальных смещений:
общий pinned source, writer ranges/SHA, reader identity и исходные tfdt/PTS
сохраняются. Существующие readers не перенастраиваются. Classic использует
собственный индексный DemuxSeek; его результат проверяется отдельно на Windows.

Этот этап не доказывает полную RF64-матрицу на больших файлах: другие rates,
mono, float/layouts, длительный stress и реальные Harvester-сессии учитываются
отдельно в [чеклисте](ProgressiveCompletionChecklist.md).
