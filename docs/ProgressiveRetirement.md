# Реестр читателей и освобождение источников вне UI

SDK 1.9, Linux Qt / Windows Qt / Windows Classic. Изменения относятся только
к FoxicMP; YouTubeHarvester не изменяется. JSON-команды и медиапрофили прежние.

## IPC-команды читателей

`readerStatus`, `readerRelease`, `readers`, `readerForget` проверяют структуру
запроса в UI без обращения к файлам, затем выполняют работу реестра в worker.
Слот реестра отдельный от подготовки/публикации медиа. Конкурирующий запрос
получает `reader_registry_busy`; Python-клиент повторяет только эти четыре
команды с этой ошибкой, в пределах общего таймаута исходного вызова.
`unknown_reader`, ошибки проверки и медиа-команды автоматически не повторяются.

Для активного `readerRelease` порядок такой: native-проверка receipt → закрытие
именно захваченного текущего источника в UI → повторная native-проверка.
ID и объект источника проверяются повторно, поэтому старый запрос не закрывает
заменивший его просмотр. Запрос, потерявший соединение до UI-стадии, не инициирует
позднее закрытие окна. Уже выполненная файловая команда не откатывается при
потере ответа. Последующие проверки release остаются обязательными.

```json
{
  "readerRegistryOffUi": true,
  "sourceRetirement": {
    "maxSources": 32,
    "workerLimit": 2,
    "processOwned": true,
    "filesClosedBeforeRelease": true
  }
}
```

## Последний владелец источника

Playback-фабрики legacy/provider и опубликованных источников используют общий
`SourceRetirement`. Перед конструированием резервируется один из 32 слотов.
В лимит входят активные объекты, очередь и выполняющиеся деструкторы. При
исчерпании новый start получает `source_limit` до открытия его файлов. После
фактического уничтожения слот можно использовать снова.

Последний `shared_ptr` ставит объект в заранее выделенную FIFO-очередь. Не более
двух process-owned worker выполняют деструкторы, joins и закрытие файлов;
на UI нет join этой очереди и отдельного cleanup-потока на каждый источник.
При недоступности второго worker допустим один. Слот освобождается только после
возврата деструктора. Это ограничение числа Source, а не общий лимит RAM, байтов,
декодеров, probes или всех потоков приложения.

Probe не удерживает playback-слот: его временный объект уничтожается в worker
самого probe до ответа. Это сохраняет контракт «probe не оставляет читателей».
Ограничения подготовки запросов и диагностического resourceProbe независимы.

## Подтверждение закрытия

`filesClosed` записывается после закрытия медиа-дескрипторов. Запись receipt
сериализована с чтением реестра через `.guard`, чтобы проверка не увидела
промежуточный JSON. Заблокированная финальная запись может ждать в cleanup-worker.
До положительного подтверждения файлы сохраняются; timeout и закрытие окна
не означают `released:true`. `readerForget` живого читателя запрещён.

После аварийного завершения процессная очередь может не успеть опустеть.
Прежняя проверка OS PID/birth и lifetime-lock остаётся основанием recovery.
Неизвестный процесс, ошибка доступа или неудачная запись маркера не превращаются
в разрешение на удаление. Гарантия «любой native read прервётся за 2 секунды»
не заявляется.

## Границы этапа

Вынесены четыре IPC-команды реестра и окончательное уничтожение указанных Source.
Закрытие графа DirectShow/renderer и часть старых блокировок ещё могут ждать I/O.
[SDK 1.10](ProgressiveLegacyOpening.md) дополнительно выносит GUI/CLI legacy opening в worker. Прямые внутренние C++ `request`/`Handle` сохраняют
синхронный совместимый путь. Все обращения к диску во всём UI этим этапом
не квалифицированы.

Медиапрофили остаются v1 MP4/M4A и v2 отдельных fMP4 H.264/AAC-LC дорожек.
Новые кодеки, live, metadata и remux — в [плане](ProgressiveIntegrationPlan.md).
SDK ZIP не обновляет опубликованные установщики 0.2.0. Установленный Linux EXE
обновлён отдельно с сохранением профиля; Windows-установки не изменялись.
[Проверки и хеши трёх сборок](ProgressiveRetirementValidation-2026-10-26.md).
