# Постраничный каталог сегментов: подготовка длинных роликов

Статус на 30 октября 2026: реализована и проверена **только общая модель**
в `shared/progressivesegmentcatalog.h`. Это проект расширения схемы 2,
а не включённый публичный API SDK 1.36. Существующие `validate`, `probe`,
`start`, `update`, CLI и playback продолжают принимать прежний inline-формат.
Capability поддержки каталога не объявляется. YouTubeHarvester не менялся.

## Зачем отдельные страницы

Увеличение одного `MaxResources` не решает задачу: основной JSON ограничен
64 KiB, старый список сегментов — 128 записями на дорожку, I/O удерживает
открытые файлы, а registry ограничен 128 читателями. Новый каталог готовит
описание большого числа сегментов; ограниченный файловый адаптер и подключение
движков остаются отдельной необходимой работой.

Каталог предназначен для двух сегментных дорожек. Поддержка медиапрофиля,
наличие декодера и воспроизведение не выводятся из успешного разбора индекса.
Модель не читает медиа, не открывает файлов и не выполняет сетевых запросов.

## Предлагаемый формат

В основном JSON схемы 2 появляется необязательный `segmentCatalog`:

```json
"segmentCatalog": [
  {
    "id": "page-0",
    "name": "page-0.json",
    "length": "24173",
    "sha256": "<64 lowercase hexadecimal characters>"
  }
]
```

`length` и SHA в примере — обозначение полей, не готовые значения для запроса.
Имя — одно переносимое локальное имя файла; разделители каталогов, Windows
device names и совпадения имён страниц запрещены. ASCII-регистр сравнивается
без учёта регистра, чтобы `page.json` и `PAGE.JSON` не стали двумя страницами
на Windows. Проверка реальной идентичности файлов и Unicode-алиасов относится
к будущему файловому адаптеру.

Каждая страница — UTF-8 JSON:

```json
{
  "version": 1,
  "sessionId": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "generation": "1",
  "writerInstanceId": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "pageId": "page-0",
  "resources": [
    {
      "id": "video-0", "name": "video-0.part", "length": "4",
      "ranges": [{"offset": "0", "length": "4"}], "state": "complete"
    }
  ],
  "tracks": [
    {
      "trackId": "video",
      "segments": [
        {
          "resourceId": "video-0", "sequence": "0", "start": "0",
          "duration": "60000000", "timestampOffset": "0",
          "discontinuity": false, "configurationId": "main"
        }
      ]
    }
  ]
}
```

Четыре байта в примере иллюстрируют модель ресурса, а не валидный fMP4.
Поля ресурса и сегмента сохраняют типы схемы 2, включая точные десятичные строки
для времени и счётчиков. `trackId` ссылается на описание дорожки в основном JSON;
страница не создаёт новые дорожки или их настройки.

## Пределы и публикация

| Ограничение | Значение |
|---|---:|
| Основной JSON | 65536 байт |
| Страницы в основном JSON | 128 |
| Одна страница | 65536 байт |
| Медиа-ресурсы в странице | 1–64 |
| Inline-ресурсы в основном JSON | не более 64 |
| Inline-сегменты одной дорожки | не более 128 |
| Все ресурсы после раскрытия, включая init | не более 8192 |
| Сегменты одной раскрытой дорожки | не более 4096 |
| Сериализованный раскрытый JSON | не более 16 MiB |

Декодер сначала проверяет все дескрипторы, затем вызывает переданный загрузчик.
Каждую полученную страницу он повторно проверяет по длине, SHA-256 и идентичности
`sessionId` / `generation` / `writerInstanceId` / `pageId`.
Предел размера нужно соблюдать **до чтения** также в будущем файловом адаптере:
проверка уже возвращённой строки не ограничивает работу произвольного callback.

Архивировать можно только ресурсы с известной положительной длиной, состоянием
`complete`, полным подтверждённым диапазоном и без `retired`. Один сегмент страницы
использует один отдельный ресурс той же страницы; неиспользуемые ресурсы
запрещены. Страница не может одновременно выступать медиа-ресурсом.
Страницы объединяются в порядке дескрипторов, затем добавляется inline-хвост.
После этого общая модель проверяет ссылки, время, последовательность, конфигурации,
состояния, имена и остальные поля схемы 2.

Writer может переносить уже опубликованный полный inline-хвост в новую
неизменяемую страницу. При обновлении `AdvanceSegmentCatalog` требует прежние
дескрипторы в неизменном порядке и вызывает обычный `Advance` раскрытой модели.
Поэтому неизменность ресурсов/сегментов сохраняется независимо от места их
описания. Уже опубликованную страницу нельзя заменить даже JSON с тем же
смыслом и другим форматированием; у него будет другой SHA-256.

SHA страницы защищает **индекс**, а не байты перечисленных медиа-файлов.
Для проверки медиа по SHA остаётся отдельный `resources[].integrity`.
Прежний `Parse(json)` сохраняет прежние пределы и отклоняет `segmentCatalog`.
Расширенный scope вызывается явно только из нового внутреннего декодера.

## Что осталось до воспроизведения длинных роликов

1. Локальный адаптер страниц: проверенное открытие без ссылок/сети, ограничение
   чтения, отмена, off-UI подготовка и корректное ожидание `waiting-index`.
2. Ограничение открытых медиа-файлов и записей читателей с проверкой идентичности
   при повторном открытии, подтверждением закрытия до освобождения lease и
   сохранением перемотки к прежним сегментам.
3. Подключение раскрытой модели к общему bridge, двум Qt-сборкам и Classic;
   согласование capability, обновлений и перезапуска сессии в Python SDK.
4. Настоящие длинные A/V-тесты трёх редакций: публикация более 64 ресурсов,
   пауза, перемотка назад/вперёд, перезапуск, ошибка страницы, отмена и release.

[Проверка модели](ProgressiveSegmentCatalogValidation-2026-10-30.md) не заменяет
эти этапы. До их завершения новая сборка/SDK с поддержкой каталога не выпускается,
а установленные приложения сохраняют проверенную реализацию SDK 1.36.
