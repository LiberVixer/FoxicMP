# Обновления progressive-сеанса вне UI

SDK 1.8, общий код Linux Qt / Windows Qt и адаптер Classic. YouTubeHarvester
не изменяется. [Первичная подготовка](ProgressivePreparation.md) дополнена
фоновыми `update`/`complete` для прежних медиапрофилей v1 и v2.

## Порядок работы

Через IPC сохраняются прежние JSON-команды и конечные ответы. В UI проверяются
поля команды, активный sessionId/readerId и допустимость операции. Рабочий поток:

1. Последовательно проверяет generation/revision, пути и опубликованные диапазоны.
2. Проверяет физические файлы и разбирает дополнительные MP4-фрагменты.
3. Применяет готовые metadata/index под короткой блокировкой состояния.

Повторной публикации на UI-стадии нет. На один профиль остаётся один рабочий
запрос подготовки/публикации; в Qt конкурирующий probe/start/update/complete
получает `preparation_busy`. Classic сохраняет последовательный pipe-клиент;
окно при этом продолжает обрабатывать сообщения. Прямые внутренние C++ вызовы
сохраняют прежний синхронный интерфейс.

```json
{
  "mediaPreparation": {
    "offUi": ["probe", "start", "update", "complete"],
    "maxConcurrent": 1,
    "responseDeadlineMilliseconds": 5000,
    "updatesOffUi": true,
    "cancellableDiskIo": false
  }
}
```

Это лимит запросов данного API, а не всех потоков декодера/проверки файлов.
Новые Python-команды не нужны: существующие PreviewSession/V2PreviewSession
продолжают работать. Прежние error codes и reader recovery сохраняются.

## Согласованность и отмена

Интерфейс, декодер и status видят последнюю применённую ревизию. Пока строится
новый индекс, доступная граница остаётся прежней. Для v2 generation/revision
остаются точными строками uint64; status не показывает новую revision раньше
готовности индекса. Новые данные становятся доступны вместе с новым состоянием.
Внутренний ResourceSource может принять диапазоны раньше, чтобы индексатор мог
читать их; внешний confirmed-prefix reader до commit использует старую границу.

Устаревшая/конфликтующая ревизия отклоняется. Ошибка структуры или generation не
заменяет действующий источник. Повреждённый индекс/изменённые подтверждённые данные
по-прежнему могут завершить сеанс с ошибкой. Отмена пользователем не превращается
в ошибку повреждённого MP4 только из-за прерывания чтения индексатора.

Stop/Close отменяют источник, не дожидаясь publication mutex. Завершившаяся после
отмены работа не возобновляет старый просмотр и не меняет новый источник.
В Classic Stop теперь закрывает progressive-сеанс и на стадии открытия DirectShow,
когда состояние ещё MLS_LOADING. Внутреннее закрытие графа не изменяет UI-owned
состояние API из графового потока через этот обработчик Stop.

**Разрыв соединения не является откатом уже начатой публикации.** Если update
вошёл в обработку действующего источника, он может успешно примениться после
потери ответа/таймаута; source при этом остаётся активным. Для v2 опросить status и
сравнить точную revision. Неподтверждённый start/удаление файлов по-прежнему требуют
readers/readerStatus/readerRelease. В v1 повтор уже принятой revision отклоняется;
следующая публикация writer использует больший revision. Не понижать счётчики.

## Блокировки и владение

В опубликованных Qt-сеансах файловое чтение декодера, проверка файлов и индексация
не удерживают metadata mutex UI. Ошибка/cancel повторно проверяются после чтения.
Classic готовит новую неизменяемую копию fragment index вне этого mutex и заменяет
оба индекса вместе со snapshot; освобождение прежних векторов также вынесено из
блокировки. В v2 диагностические счётчики используют атомарные значения и стабильную
инкарнацию writer, не ожидают I/O mutex. Это не криптографическая integrity-проверка.

Копирование индексов Classic имеет дополнительную цену CPU/RAM в worker; старый
предел 2 млн samples сохраняется. Пиковая память на предельных индексах и длительная
нагрузка этим этапом не квалифицированы. Положительный released выдаётся после
фактического закрытия файлов последним владельцем, включая рабочий запрос.

## Что ещё не закрыто

Весь пункт ТЗ о неблокирующем I/O пока не объявляется завершённым. Остались
legacy/provider opening и часть его старых блокировок, файловые операции registry
читателей на UI, некоторые пути конечной деинициализации/закрытия и ожидания ОС.
Native read/open не прерывается принудительно: нет общей гарантии закрытия любого
дескриптора за 2 секунды. Асинхронная публикация сама по себе не решает зависание
драйвера или файловой системы.

Медиапрофили прежние: v1 MP4/M4A и две отдельные v2 fMP4 H.264/AAC-LC дорожки.
Новые кодеки, универсальный demux/remux, live/metadata и реальный Harvester остаются
в [плане](ProgressiveIntegrationPlan.md). Установщики 0.2.0 не обновляются SDK ZIP.
[Проверки трёх редакций](ProgressivePublicationValidation-2026-10-26.md).
