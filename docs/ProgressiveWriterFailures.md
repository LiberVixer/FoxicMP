# Progressive: авария writer, неполный PCM-кадр и ENOSPC

Проверка от 3 ноября 2026 года, приложение 0.2.0, контракт SDK 1.81.
[Полные измерения и exit codes](ProgressiveWriterFailuresValidation-2026-11-03.json).
Это проверка существующего поведения плеера отдельными тестовыми writer-процессами.
Harvester не изменяется. Production-исправлений не потребовалось; EXE и профили
сохранены, установленный Linux уже совпадает с проверенным бинарным файлом.

## Сценарии трёх редакций

В каждой редакции работают два самостоятельных процесса плеера. Один получает
сессию от writer-процесса, который действительно выполняет start/update,
запись, flush/fsync, heartbeat и сообщение об ошибке. Второй плеер читает
независимый контрольный источник от отдельного тестового writer-контроллера.
Профили, файлы и endpoints изолированы от установленных приложений.

Проверяются четыре RF64-профиля: PCM16/PCM24 stereo 48 kHz, обычный и sparse hint.
Каждый проходит два отказа — принудительное завершение writer и инъекцию ENOSPC.

| Редакция | Сценарии | Завершений writer | Инъекций ENOSPC | Exit драйвера |
|---|---:|---:|---:|---:|
| Linux Qt | 8 | 4 | 4 | 0 |
| Windows Qt | 8 | 4 | 4 | 0 |
| Windows Classic | 8 | 4 | 4 | 0 |

Код завершения убитого writer — -9 в Linux и 1 в Windows; это ожидаемое
внедрение отказа, отдельно от exit 0 драйвера. Recovery/error writers нормально
завершаются с exit 0. Сам плеер остаётся живым во время всех сценариев;
два его пустых тестовых процесса принудительно завершаются только при очистке,
после положительных filesClosed. Все коды сохранены в отчёте.

## Неполная запись и исчезновение heartbeat

Writer публикует 4 s, затем 12 s из известных 20 s. Плеер действительно
воспроизводит источник: проверяются playing, clock и decoder I/O.
После этого writer физически дописывает неполный следующий PCM-кадр —
3 байта для PCM16 stereo или 5 для PCM24 stereo — и делает flush/fsync,
но **не публикует** эти байты в ranges/integrity.

В crash-сценарии родитель завершает только собственный writer через Popen.
Плеер не получает error/cancel/complete. Наблюдатель обращается к status,
не посылая heartbeat этому источнику. Минимум 16 s проверяется:

- источник не становится complete/finished/error/cancelled;
- физический размер файла не расширяет доступную границу сверх 12 s;
- после штатного 15-секундного heartbeat deadline возникает waiting-downloader;
- reader плеера остаётся lease-held, его PID принадлежит живому плееру,
  а не завершённому writer; нет ложного filesClosed/release;
- опубликованный префикс и неполный физический хвост сохранены.

Контрольный writer продолжает собственный heartbeat. Его источник может
штатно дойти до границы буфера; последующая допубликация достаточного объёма
возобновляет реальное воспроизведение с тем же readerId. Отказ первого writer
не отменяет контрольную сессию и не удаляет её файл.

## Явное восстановление writer

Новый writer-процесс независимо сверяет SHA-256 прежнего опубликованного
префикса и содержимое физического хвоста с ожидаемыми байтами. Новый instanceId
не принимается в активное прежнее поколение: попытка start получает
`generation_changed`. После этого выполняется явный replace с generation 2,
сохраняющимися sessionId и физическим файлом.

Новый writer дописывает отсутствующие байты неполного кадра и данные до 16 s,
не переписывая опубликованный префикс. Только после записи/flush создаётся
новый подтверждённый снимок. Плеер открывает новый reader, реально воспроизводит
его и сохраняет тот же device/fileId. Прежний reader закрывается штатно
с filesClosed при замене, при том же живом PID плеера — не из-за смерти writer.
Даже нормальный выход recovery writer сам по себе не освобождает новый reader.

Это явное повторное открытие тестовым загрузчиком, без автоматического
восстановления позиции/ручной паузы и без реализации durable checkpoint в Harvester.

## Ошибка ENOSPC

Второй сценарий сначала выполняет настоящую короткую запись и flush/fsync,
затем **в тестовом writer** поднимает OSError ENOSPC. Это управляемая инъекция
ошибки после short write. Файловая система, квота или RAM disk не заполняются;
реальный kernel disk-full этим этапом **не проверен**.

Writer сообщает ENOSPC через существующее публичное действие `error`.
Проверяются состояние error и сохранённая причина, отсутствие complete/finished,
сохранность опубликованных байтов и неопубликованного хвоста. Ни плеер,
ни драйвер не удаляют исходник при получении ошибки. Контрольная сессия остаётся
независимой и может продолжить чтение. После явного release подтверждается
filesClosed; файл удаляется только на завершающей стадии теста.

Здесь проверено сообщение об ошибке через API, а не все варианты failed snapshot,
реальная ошибка WriteFile/write на заполненном томе или retry после освобождения места.

## Воспроизведение и границы

Общий драйвер и writer: `tests/progressive_writer_failures.py`.
Qt CTest — `progressive-writer-failures`, timeout 480 s. Linux запускается через
`qt/tests/run_tests.sh` с частными X11/D-Bus/PulseAudio. Classic использует
две временные portable-копии с ContextMenuPrompted=1/ContextMenuEnabled=0.
Установленные Windows EXE/INI, Linux EXE/INI, 158 Classic shell entries,
публичный SDK ZIP и Harvester не менялись. Все свои процессы, reader directories,
sockets/locks, одноразовые задачи и staging-копии удалены.

Первый прогон теста дописывал контрольный поток только с 12 до 16 s:
около его границы этого недостаточно для штатного порога возобновления 5 s.
Исправлен только тест: контрольные bytes публикуются до 20 s без writer complete.
Начальные exit 8 Qt/exit 1 Classic сохранены; пороги и настройки плееров не менялись.

Срез ограничен указанными RF64, последовательными prefixes и одним неполным
PCM-кадром. Не проверены crash внутри syscall записи, потеря питания/данных
после fsync, повреждённый checkpoint, настоящая заполненная файловая система,
полная codec/container matrix, rename/final-file transition, reboot, mixed-edition
и длительная нагрузка. [Общий чеклист](ProgressiveCompletionChecklist.md) сохраняет
эти критерии открытыми.
