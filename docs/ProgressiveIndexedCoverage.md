# Подтверждённые временные интервалы continuous cache

8 ноября 2026. Внутренний общий компонент Qt/Linux, Qt/Windows и Classic.
Приложение 0.2.0, публичный SDK 1.84; новый контракт перемотки не объявлен.
[Измерения, SHA и точные exit codes](ProgressiveIndexedCoverageValidation-2026-11-08.json).

## Что добавлено

`StreamIndexedCoverage` объединяет presentation-интервалы только тех samples,
чьи полные moof/mdat уже проверены и опубликованы общим cache index.
Порядок поступления может отличаться от PTS: поздний кадр не заполняет
пропуск перед собой. Отрицательная часть priming не увеличивает покрытие.
Каждый новый sample обрабатывается один раз; накопленные раздельные интервалы
ограничены существующим лимитом 50 000 packets. Запрос status копирует готовые
числа и не сканирует индекс или файл. Общая ресурсная приёмка этим не закрыта.

Внутренний `StreamCacheStatus` и частный cache fixture содержат:

| Поле | Значение |
| --- | --- |
| `videoIndexedEnd100ns` | Конец непрерывного объединения видеоинтервалов от нуля |
| `audioIndexedEnd100ns` | Такое же покрытие AAC, ограниченное точным PCM-окном |
| `audioIndexedComplete` | Все AAC packets точного неизменяемого PCM-плана проверены |
| `indexedEnd100ns` | Минимум дорожек; завершённый конечный AAC больше не ограничивает видео |

Для полностью проверенного AAC конечная граница берётся из точного числа PCM
samples: округление MP4 clock может отличаться на один tick. Это завершение
одной дорожки, а не producer EOF. При ошибке кэша или его удалении поля
покрытия обнуляются; счётчики прежних samples остаются диагностическими.

## Что ещё не разрешено

Покрытие PTS само по себе не доказывает наличие decoder dependencies,
ключевого кадра/preroll, пригодность demuxer к seek или успешное декодирование.
Конец последнего packet также не заменяет заявленную duration источника.
Эти поля не являются разрешением на чтение: SHA, leases и reader admission
сохранены. Частичный moof/mdat не публикуется, конец растущего файла остаётся
`waiting-range`, а не EOF. Поля пока не добавлены в публичный IPC/SDK/UI.

Публичный `continuousPlaybackControl seek` по-прежнему требует завершённый
output. Следующий этап — отдельный совместимый opt-in для growing seek:
decoder-safe границы, backend-проверки трёх редакций, ожидание недоступной
позиции, пауза/замена/отмена и защита от ложного EOF. После этого можно
объявлять capability и выводить временной буфер в API/UI.

## Проверка

- GCC/Linux, ASan/UBSan/Linux, MinGW/Windows и MSVC/Windows: по 40 013
  проверок независимым oracle интервалов, включая перестановку, пробелы,
  перекрытия, отрицательные timestamps и INT64 boundaries; native exit 0.
- По 22 managed-AAC и 31 прежнему cache scenario каждого toolchain:
  всего 212, native exits 0. Шесть реальных H.264/AAC профилей, 44,1/48 kHz,
  mono/stereo, fractional clocks, B16, aligned и одноотсчётный звук перед видео.
  По 42 согласованных снимка покрытия на toolchain сверены с независимым
  сортирующим oracle и проверяемыми packet payload/clocks. Проверены частичные
  fragments, растущий input, конечный короткий AAC, ошибки и cleanup.
- Новый CMake target `foxicmp-progressive-stream-coverage-tests` собран;
  `ctest -R '^progressive-stream-indexed-coverage$'` прошёл, exit 0.

Первый MSVC managed-прогон отвергнут заключительным SHA guard: файл теста
изменили во время исполнения. Все его 22 сценария и child exits были успешны,
но общий native exit 1 сохранён. Повтор с зафиксированным исходником прошёл;
первый отказ не переименован в PASS. SHA первой и конечной версий записаны
в отчёте; реконструкция первой версии совпадает с SHA начального GCC-прогона.

Это native component-проверка общих заголовков обоими Windows toolchains,
не новый main Player/graph и не измерение физической A/V синхронизации.
Main EXE, worker, SDK/публичные assets и установленные версии не заменялись;
583 защищённых файла и 158 HKCU shell entries совпали до/после. Harvester,
профили и настройки Windows не менялись; одноразовые задачи не создавались.
