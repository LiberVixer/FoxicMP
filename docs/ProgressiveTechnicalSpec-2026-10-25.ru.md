# Техническое задание: универсальный просмотр загрузок Harvester в FoxicMP

Дата: 25 октября 2026 года. Статус: ТЗ для разработки, не отчёт о реализованной поддержке.

## 1. Цель и редакции

Обеспечить воспроизведение медиа из YouTube, VK и Rutube непосредственно во время скачивания Harvester: до получения полного файла, до объединения видео и аудио, с доступными аудиодорожками, субтитрами, главами и метаданными.

Требование распространяется на три самостоятельные редакции:

1. FoxiqMP qt для Linux.
2. FoxiqMP qt для Windows.
3. FoxicMP Classic для Windows.

У редакций едины контракт загрузчика, правила готовности данных, пользовательский результат и критерии приёмки. Qt-код общий; Classic сохраняет свой интерфейс и DirectShow-архитектуру. Профили, регистрация приложений и установочные каталоги остаются независимыми.

Основание: локальный аудит FoxicMP, коммит `49e6b0af91b81dbcc3c100fc76838b284dab3a7c`, проект `/media/sf_Studio/Programs/MPMY-src`; отчёт `/home/redmin/YTD/docs/foxicmp-compatibility-audit-20261025-ru.md`.

## 2. Что означает «любые недокаченные файлы»

Цель: все незашифрованные контейнеры, кодеки и дорожки, реально выдаваемые поддерживаемыми сценариями Harvester для трёх сервисов и декодируемые поставляемым backend. Поддержка определяется содержимым, а не расширением файла или названием сервиса.

Нельзя требовать воспроизведения байтов, которые ещё не получены, отсутствующего ключевого кадра, неизвестного кодека, неполученного обязательного индекса или DRM без законно доступного ключа. Поэтому API обязан различать:

- поддерживаемый источник, готовый к просмотру;
- поддерживаемый источник, ожидающий данные, заголовки, индекс или ключевой кадр;
- источник, требующий локальной подготовки/remux;
- источник, доступный только после полной загрузки;
- окончательно неподдерживаемый, зашифрованный либо повреждённый источник.

Ожидание полного файла считается корректным ограничением, но НЕ успешным выполнением требования просмотра во время скачивания. Нельзя скрывать такой результат под словом fallback. Для каждого обязательного положительного сценария приёмка требует реального старта ДО завершения загрузки.

Старт не привязывается к 5% или другому проценту: достаточно подтверждённых заголовков и общего воспроизводимого интервала. Невозможность раннего старта объясняется конкретной причиной.

## 3. Четыре обязательных пункта по результатам аудита

### F-01. Снять ограничение H.264/AAC/MP4

Заменить единственный узкий progressive path расширяемым слоем чтения и демультиплексирования. Сохранить проверенный H.264/AAC путь, но добавить остальные обязательные контейнеры и кодеки из раздела 5, отдельные и совмещённые дорожки, несколько аудиодорожек и субтитры.

Режимы должны различаться явно: `native-progressive`, `progressive-remux`, при отдельно согласованной необходимости `progressive-transcode`, `post-download`, `unsupported`. Remux работает только с уже скачанными локальными данными, не меняет сжатые потоки и не ухудшает качество. Перекодирование по умолчанию запрещено и не засчитывается как сохранение исходного качества.

### F-02. Обеспечить подключение Harvester к новому API

В FoxicMP предоставить стабильный API, поставляемый клиент и эталонный адаптер к событиям загрузки. Они должны поддерживать обнаружение, проверку возможностей, пробу источника, запуск, публикацию записанных данных, heartbeat, завершение, ошибку, отмену и освобождение файлов.

Текущее принудительное отключение предпросмотра в Harvester не исправляется одним изменением плеера. Работы разделить: команда FoxicMP делает API, SDK и воспроизводимый интеграционный стенд; подключение кнопки и событий в Harvester является отдельной обязательной зависимостью общей приёмки. Самостоятельно включать приостановленную функцию или менять Harvester в задаче плеера нельзя.

Пока реальный Harvester не подключён и не пройден сквозной сценарий, разрешён статус «плеер готов к интеграции», но не «полная совместимость Harvester готова».

### F-03. Исправить sessionDirectory в Windows Classic

После успешного `start` сохранять нормализованный каталог сеанса. При `update/complete` без явно заданного каталога использовать сохранённый. Замена, закрытие и новый сеанс не должны наследовать каталог предыдущего сеанса. Явное изменение каталога активных дорожек отклонять.

Добавить общий regression-сценарий: относительные имена -> `start` с каталогом -> несколько `update` и `complete` без каталога -> нормальное завершение. Один сценарий обязан проходить в Linux Qt, Windows Qt и Classic.

### F-04. Унифицировать запуск, включая Windows Qt

Единый рекомендуемый способ для всех редакций: player-owned API. Нельзя требовать от Harvester самостоятельных Win32-операций или другого JSON для каждой редакции.

Для существующих CLI-входов сохранить совместимость либо реализовать адаптер старого манифеста/provider к новому API. В частности, Windows Qt не должна просто отвергать прежний способ без документированного пути миграции. Адаптер обязан реально передавать обновления и состояние writer, а не только открыть первоначальные файлы.

Старые leases и новый API согласовать явно: закрытие плеера освобождает только читателя, не отменяет скачивание; загрузчик не удаляет источники до освобождения всех читателей. Новая интеграция не должна зависеть от неподключённого старого provider.

## 4. Архитектурные требования

- Использовать проверенные FFmpeg/libavformat/libavcodec, libmpv и существующие DirectShow-компоненты, а не создавать собственный универсальный декодер.
- Общими сделать модель сеанса, проверку диапазонов, capabilities, временную шкалу, ошибки и conformance-тесты. Отличия OS и media backend оформить отдельными адаптерами.
- Для Qt использовать один media clock libmpv для видео и выбранного аудио. Для Classic сохранять синхронизацию DirectShow graph; новые источники подавать через совместимый reader/source filter.
- Ввод читателя предоставляется через контролируемый I/O-слой с отменяемым ожиданием диапазона. Физический конец растущего файла не означает EOF.
- Парсинг, probe, индексирование, remux и ожидание диска не блокируют UI. Не удерживать общий mutex во время неограниченного ожидания I/O.
- Полученные потоки не открывать как обычные завершённые файлы с надеждой, что backend сам заметит увеличение размера. Поведение ожидания и EOF должно контролироваться явно.
- Плеер не обращается к исходному URL, не запускает вторую загрузку и не получает cookies/токены Harvester. Remux не меняет оригиналы и не мешает итоговой сборке загрузчика.
- Выпуск фиксирует версии backend, build options и доступные декодеры; capabilities соответствуют конкретной сборке, а не теоретическим возможностям библиотеки.

## 5. Обязательная матрица медиа

Поддержать каждый перечисленный формат в допустимых для него сочетаниях. Матрица не означает, что любой кодек обязан помещаться в любой контейнер.

| Область | Обязательный охват |
| --- | --- |
| Контейнеры | MP4/M4A/MOV: fast-start, fragmented, индекс в конце; WebM/Matroska; MPEG-TS; ADTS AAC; MP3; Ogg; FLAC; WAV/PCM |
| Видео | H.264, HEVC/H.265, VP9, AV1, VP8; MPEG-2/MPEG-4 Part 2 при наличии таких загрузок/локальных входов |
| Аудио | AAC-LC, HE-AAC, Opus, Vorbis, MP3, FLAC, PCM, AC-3/E-AC-3 |
| Варианты дорожек | video-only, audio-only, muxed A/V, отдельные A/V, несколько языков/аудиодорожек; моно, стерео, многоканальный звук |
| Субтитры | SRT, WebVTT, ASS/SSA, TTML; сервисные текстовые варианты, например YouTube JSON3/SRV, через документированный адаптер; встроенные mov_text, WebVTT, ASS, SubRip |
| Графические субтитры | PGS/DVD subtitle при наличии в локальном контейнере; обязательные заголовки/палитры учитываются при готовности |
| Доставка | Прямой HTTP(S), конечные HLS и DASH, последовательная и параллельная запись сегментов; плеер получает только локальный результат загрузчика |
| Дополнительные данные | Главы, названия и языки дорожек, default/forced flags, длительность, обложка, HDR/color metadata, поворот, aspect ratio, variable frame rate |

Новый формат, обнаруженный в актуальном корпусе YT/VK/Rutube, добавляется в реестр поддержки и тесты. Файл, воспроизводимый после полной загрузки, не должен необъяснимо объявляться «кодек не поддерживается» только из-за незавершённости.

Для расширений вне матрицы использовать `probe` с объяснимым результатом. DRM, испорченные потоки, неизвестные декодеры и иные объективные исключения фиксировать отдельно; обход защиты не входит в ТЗ.

## 6. Чтение неполных файлов и сегментов

- Публикуются только записанные и видимые другому процессу байты. Сетевой счётчик и `stat().st_size` sparse-файла не подтверждают данные.
- Для последовательной записи использовать непрерывный префикс; для параллельных фрагментов поддержать карту подтверждённых диапазонов и порядок сегментов.
- Незаписанные дыры не читать как нули. Не выдавать `complete`, если существуют обязательные пробелы.
- Частичные заголовки, atom, EBML cluster, TS packet, codec packet и subtitle cue не передавать как законченные структуры; ожидать достаточных данных.
- MP4 с `moov` в конце: ожидать индекс либо запросить у загрузчика приоритетный диапазон метаданных, если он поддерживает такую операцию. Сам плеер не скачивает хвост. Без индекса/достаточной реконструируемой информации не обещать декодирование.
- Если источник допускает потоковый remux, начинать подготовку до завершения загрузки, без ожидания полного входа. Контейнер выхода выбирать по совместимости всех включённых потоков, а не всегда MP4.
- Remux не является способом обойти отсутствие входного индекса или декодера. Такая причина возвращается как ожидание/ограничение.
- HLS/DASH: учитывать init segments, timeline, последовательности, discontinuity, смену timestamp origin и доступность ключевых кадров. Смена несовместимого codec configuration требует контролируемой переинициализации, а не чтения старым декодером.
- Для live/event HLS и динамического DASH поддержать отдельный режим с движущимся окном и неизвестной длительностью; выход сегмента из окна объяснять. Конец определяется явным событием writer, не отсутствием следующего сегмента.
- Переименование при финализации не прерывает чтение закреплённых дескрипторов. Перезапись/усечение опубликованного содержимого обнаруживается и завершает соответствующий сеанс понятной ошибкой.
- Возобновление той же загрузки разрешено только при подтверждении идентичности ранее опубликованных данных; иначе нужен новый сеанс/поколение без использования старых индексов.

## 7. Протокол и поставляемый клиент

Существующий `progressive-manifest-v1` сохранить для совместимых двухдорожечных MP4-сценариев. Новый набор возможностей оформить отдельной согласованной версией схемы: несколько дорожек, сегменты, диапазоны, optional streams и live нельзя молча добавлять как обязательные поля v1.

Контракт должен определять:

- согласование версий и возможностей до начала просмотра;
- уникальный `sessionId`, поколение и монотонную ревизию, стабильные идентификаторы дорожек;
- абсолютный `sessionDirectory` и безопасные локальные имена ресурсов; каталог сохраняется на срок сеанса;
- тип, codec/container hints, язык, label, default/forced, обязательность дорожки и начальную готовность; hints проверяются по содержимому;
- записанные диапазоны/префиксы, ожидаемый размер или неизвестную длину, состояние каждого ресурса;
- duration, timebase, timestamp offset, edit lists, сегментную шкалу и признак live;
- независимые потоки обновления глав, субтитров и метаданных;
- состояние writer отдельно от состояния playback; завершение каждой дорожки отдельно от завершения сеанса;
- команды discovery/capabilities/probe/start/update/heartbeat/complete/error/cancel/status/release; выбор дорожек и seek с ответом о доступности;
- согласуемый запрос нужного диапазона/приоритета загрузчику; при отсутствии поддержки честный переход в ожидание;
- точное представление 64-битных смещений/времени без потери разрядов через JSON floating point;
- ограничение размеров и числа объектов, фрейминг, таймауты, обработку дублей команд/ключей и правила восстановления соединения.

Большие наборы глав/субтитров передавать отдельными ограниченными порциями или безопасными локальными ресурсами, не отменяя лимит командного канала ради одного огромного JSON.

`probe` возвращает машинные коды: например `waiting-initialization`, `waiting-index`, `waiting-keyframe`, `waiting-range`, `missing-decoder`, `encrypted-source`, `corrupt-source`, `unsupported-container`. Временную нехватку данных нельзя классифицировать как окончательный отказ. `ok=true` при принятии команды не равнозначно `state=playing`.

Поставить Python-клиент с одинаковым публичным интерфейсом на Linux и Windows, CLI-примеры и стенд writer. OS transport выбирается внутри клиента: Unix domain socket либо защищённый Windows named pipe. Обнаружение не изменяет пользовательский профиль; автозапуск не перехватывает чужой сеанс просмотра.

## 8. Аудио, видео и синхронизация

- Сохранять PTS/DTS, отрицательный preroll, edit lists, sample rate, channel layout и gapless metadata. Не обнулять каждую дорожку независимо.
- Общая воспроизводимая граница определяется обязательными выбранными A/V потоками; optional субтитры и обложки не блокируют старт.
- Начальные ориентиры буфера: старт 10 секунд, повторный старт 5 секунд, остановка при запасе менее 1 секунды; завершённые короткие файлы запускаются сразу. Для live параметры и целевая задержка задаются отдельно.
- Более быстрая дорожка не убегает вперёд более медленной. При возобновлении восстанавливать синхронизацию, а не увеличивать постоянный A/V offset.
- Переключать язык/аудиодорожку без перезапуска загрузки; при нехватке соответствующих данных показать ожидание. Не применять молча другую дорожку.
- Video-only и audio-only не ждут несуществующего второго файла. Отсутствие звукового устройства не превращает валидный video-only источник в ошибочный.
- Поддержать программное декодирование при недоступном GPU. Не обещать плавный 4K AV1 на оборудовании, не способном декодировать его в реальном времени.
- Перемотка разрешена только при наличии нужных данных и точки декодирования. Запрос за границу возвращает причину/ожидание, а не ложный успех или зависание.
- До complete перемотка может зависеть от кэша; после complete обеспечить обычные возможности seek либо явно переоткрыть источник с сохранением позиции/паузы.

## 9. Субтитры, главы и метаданные

- Субтитры добавляются и обновляются во время просмотра; поддерживаются встроенные и внешние дорожки, ручные и автоматические субтитры.
- Для текстовых потоков учитывать границы UTF-8/UTF-16, BOM и неполные cues. Показывать только завершённые события; повторная публикация не дублирует строки.
- Сохранять временную шкалу, ASS styles, WebVTT settings, supported TTML styling и forced/default/language flags. Ограничения конвертации описать; нельзя выдавать потерю оформления за полную поддержку исходного формата.
- Позднее появление субтитров не требует перезапуска A/V. Ошибка optional дорожки не останавливает видео; пользователь получает причину и возможность выбрать другую дорожку.
- Шрифты/вложения контейнера обрабатывать с ограничениями размера и безопасности; не устанавливать их в систему. HTML/XML не загружает внешние ресурсы, TTML не использует внешние сущности.
- Главы принимать из контейнера и метаданных Harvester. У них стабильные ID, время, название и проверенные границы. Обновление не меняет текущую позицию и не создаёт дубликаты.
- Главы за доступной границей можно показывать, но переход к ним подчиняется правилам доступности. Отсутствующая финальная длительность не ломает список.
- Обложки и preview не блокируют воспроизведение; сохраняются цветовые параметры, ориентация и сведения о дорожках. Итоговая склейка не должна терять эти данные из-за режима просмотра.

## 10. Жизненный цикл и безопасность

- Пропавший heartbeat означает ожидание/разрыв writer, но не EOF. Подтверждённая гибель writer и явные error/cancel обрабатываются отдельно.
- Stop/Close/Cancel должны прерывать ожидания чтения, декодера и remux. Закрытие плеера не останавливает загрузчик без отдельного действия пользователя.
- Ошибка предпросмотра не отменяет обычную загрузку и не меняет архив Harvester. Ошибка writer не маскируется успешным концом видео.
- Все читатели учитываются по session и reader ID; PID проверяется вместе с временем создания либо эквивалентной идентичностью процесса. Истечение времени само по себе не даёт права удалить используемые дорожки.
- Плеер читает входы, но не удаляет и не переписывает их. Его собственные промежуточные remux-файлы отделены от источников и имеют ограниченную политику очистки.
- IPC доступен текущему пользователю; проверяются владелец, тип файла, диапазоны, reparse points/симлинки, обход каталога и подмена пути. Нельзя использовать URL, устройства и произвольные команды как ресурс сеанса.
- Обработать Unicode, пробелы и длинные пути без нынешнего прикладного лимита Classic в 240 символов, в пределах возможностей ОС. Неподдерживаемый filesystem возвращает точную ошибку.
- Сетевые и сменные носители не считать гарантированно поддержанными: возможности объявляются отдельно, подтверждаются тестами идентичности, одновременной записи/чтения и отключения носителя. Локальный fixed drive является обязательной базовой средой.
- Логи не содержат cookies, ключи, подписанные source URL и другие секреты. Детальные диагностические трассы включаются явно.

## 11. Интерфейс и диагностика

Показывать название ролика, источник, выбранные дорожки, доступную временную границу, состояние буфера и конкретную причину ожидания. Отличать «скачивание продолжается», «подготовка локального потока», «просмотр недоступен до получения индекса», «неподдерживаемый кодек» и «ошибка загрузки».

Пользовательские Pause/Stop/Seek, выбор аудио/субтитров и главы должны оставаться работоспособными. Ручная пауза сохраняется после поступления данных и complete. Фоновый start не активирует окно, если клиент запросил `activate=false`.

В диагностике фиксировать session/reader ID, редакцию, backend, выбранный режим, codec/container, готовые диапазоны, позицию, причину буферизации и переходы состояния. Должны быть доступны версии компонентов и машиночитаемый результат пробы источника.

## 12. Матрица испытаний

Для каждой редакции выполнить один общий conformance-корпус, затем её backend/OS проверки. Все положительные и отрицательные случаи имеют ожидаемый результат, а не просто отсутствие падения.

| Группа | Обязательные сценарии |
| --- | --- |
| Четыре пункта аудита | v1 совместимость; новый API; Classic relative start/update/complete; Windows Qt через клиент и legacy-адаптер |
| Форматы | Допустимые сочетания из раздела 5; отдельные и muxed A/V; audio-only/video-only; 8/10-bit, VFR, HDR metadata, многоканальный звук |
| Запись | Медленное видео/быстрое аудио и наоборот; паузы writer 10/30/60 секунд; out-of-order сегменты; sparse holes; частичные заголовки/пакеты |
| Индексы | moov в начале/конце, fMP4, WebM без финальных cues; отсутствие индекса до его публикации; приоритетный диапазон при поддержке writer |
| Время | Отрицательные PTS, preroll AAC, edit lists, разные начала дорожек, discontinuity, смена init segment, VFR |
| Дорожки | Смена языка, несколько аудио, поздние субтитры, неполный cue, ASS/TTML styles, главы с обновлениями, повреждённая optional дорожка |
| Протокол | Старые revision/generation, дубли ключей и команд, пределы JSON, неизвестная версия, неверные диапазоны, heartbeat/reconnect, замена сеанса |
| Файлы | Переименование, запрещённое усечение/подмена, права, Unicode/длинные пути, заполнение диска, несколько читателей, безопасная очистка |
| Завершение | Разный порядок окончания дорожек, ошибка merge, отмена writer, аварии плеера/writer, Stop/Close при зависшем чтении/remux, итоговый файл |
| Сервисы | Реальные разрешённые пользователем загрузки YT/VK/Rutube: direct/HLS/DASH там, где они фактически доступны; рядом сохранённые offline fixtures |
| Исключения | DRM/шифрование, повреждённый индекс, неизвестный кодек, отсутствие ключевого кадра и неполученные данные: правильная причина, без ложного PASS |

Не считать заголовок теста «VK» подтверждением всех форматов VK. Для каждого реального источника сохранять extractor/protocol/format IDs, контейнеры, кодеки, дорожки и результат, без секретных URL. Live проверяется отдельно от конечных роликов.

Стенд замедляет writer и удерживает завершение, чтобы доказать просмотр минимум 10 секунд до complete. Простое открытие полностью скачанного файла не засчитывается. Локальный тест проверяет единственную загрузку каждого ресурса; для сети разрешены необходимые retries/range requests, но запрещена независимая загрузка плеером.

## 13. Критерии приёмки

1. F-01..F-04 закрыты реализацией и общими тестами во всех трёх редакциях; API capabilities соответствует поставляемым бинарникам.
2. Все положительные строки согласованной матрицы реально воспроизводятся до complete. Невыполненная обязательная строка остаётся блокером, даже если показан корректный post-download fallback.
3. На согласованном эталонном ПК с достаточной производительностью старт после получения готового буфера занимает не более 3 секунд, возобновление после его восстановления не более 2 секунд; для remux время подготовки измеряется отдельно.
4. На тестах с измеримой flash/beep-разметкой абсолютная A/V ошибка после стабилизации не превышает 80 мс, накопленный дрейф за 30 минут не превышает 40 мс. Параметры ПК, latency устройства и метод измерения фиксируются; software timestamps не выдаются за измерение физического звука.
5. Stop/Close/Cancel освобождает управляемые ожидания не более чем за 2 секунды; зависший внешний процесс завершается ограниченной процедурой. UI не зависает при отсутствующих данных.
6. Нет чтения неопубликованных диапазонов, преждевременного EOF, повреждения итогового файла, потери выбранных дорожек/глав/субтитров и незапрошенного ухудшения качества.
7. Проверены длинная загрузка, минимум 100 циклов start/cancel и несколько читателей; нет нарастающих утечек памяти, потоков и дескрипторов. Лимиты RAM/кэша/temp и нагрузка фиксируются для каждой редакции и режима.
8. Обычное воспроизведение завершённых файлов и пользовательские настройки не регрессировали. Тесты используют отдельные профили и не меняют установленную регистрацию приложений.
9. Есть сквозные успешные проверки из реального Harvester в Linux Qt, Windows Qt и Classic. Без них окончательная общая совместимость не принимается.
10. Для каждого ограничения есть reasonCode, пользовательское сообщение и отрицательный тест. Необъяснимые SKIP, ожидание полной загрузки в обязательном progressive-сценарии и неподтверждённые Windows результаты не засчитываются как PASS.

## 14. Порядок реализации и результаты поставки

1. Исправить Classic sessionDirectory и зафиксировать существующий v1 контракт regression-тестами.
2. Унифицировать discovery/client/start и миграцию старого способа открытия, включая Windows Qt.
3. Согласовать расширенную схему, модель дорожек/диапазонов и безопасный жизненный цикл читателей.
4. Реализовать расширенные demux/readers и progressive-remux; подтвердить основные H.264/HEVC/VP9/AV1 и AAC/Opus сценарии, затем всю обязательную матрицу.
5. Добавить несколько дорожек, субтитры, главы, метаданные, HLS/DASH timeline и live.
6. Подключить отдельную задачу Harvester и выполнить общую приёмку трёх редакций; после этого обновить документацию и пакеты.

Поставка включает исходники, новые тесты и fixtures с известным происхождением, спецификацию схемы и ошибок, клиент/legacy-адаптер, интеграционный writer-стенд, инструкции Harvester, три сборки, версии/лицензии компонентов и отчёт матрицы с точными exit codes. Зависимости и тестовые активы должны быть воспроизводимы; DRM-ключи и личные данные в поставку не входят.

Обещание «любой формат» допускается только как направление развития. Публичная формулировка должна точно перечислять проверенные возможности и объективные ограничения; наличие FFmpeg/libmpv само по себе не является доказательством выполнения ТЗ.
