# Progressive: завершение процесса плеера и восстановление readers

Проверка от 3 ноября 2026 года: приложение 0.2.0, контракт SDK 1.81.
[Полные результаты, exit codes и SHA-256](ProgressivePlayerCrashRecoveryValidation-2026-11-03.json).
В этом срезе ошибок программы не обнаружено: добавлены воспроизводимый тест,
его CTest-регистрация и документация. Production EXE, настройки и опубликованные
SDK/release assets не изменялись.

## Настоящие отдельные процессы

Для каждой редакции запускаются два самостоятельных процесса с независимыми
профилями и endpoints. Они используют один физический недокачанный RF64.
Проверены PCM16 и PCM24, stereo 48 kHz: два принудительных завершения во время
реального воспроизведения и два при буферизации с четырьмя подтверждёнными
секундами. Во всех случаях второй плеер уже действительно воспроизводит файл.
В отличие от предыдущего Qt multi-reader теста здесь Qt-плееры тоже работают
**в разных процессах**, а не в двух Window одного тестового процесса.

Перед завершением первый процесс держит три активные квитанции: внешнюю группу
воспроизведения, внутренний файловый reader и дополнительную I/O-проверку,
ожидающую неподтверждённого участка на 18 s. Второй процесс держит ещё две.
Проверяются их реальные PID/birth, физические device/fileId и запрет forget
живого reader. Отдельная native-утилита также подтверждает lease-held до аварии.

Внедрение отказа выполняется только через собственный Popen: SIGKILL в Linux
и TerminateProcess в Windows. Это проверка принудительного завершения процесса,
а не воспроизведение конкретного исключения плеера, reboot или отказа ОС.

| Редакция | Активных завершений | Восстановленных квитанций | Exit дочернего процесса | Exit драйвера |
|---|---:|---:|---:|---:|
| Linux Qt | 4 | 12 | -9 | 0 |
| Windows Qt | 4 | 12 | 1 | 0 |
| Windows Classic | 4 | 12 | 1 | 0 |

Ненулевой exit code принудительно завершённого дочернего процесса здесь ожидаем.
Он сохраняется отдельно от exit code тестового драйвера. После положительного
освобождения всех readers драйвер также завершает два оставшихся **пустых**
тестовых процесса; эти дополнительные cleanup exits не считаются активными
авариями. Их точные коды и назначение находятся в processHistory отчёта.

## Что подтверждает освобождение после аварии

Отсутствие IPC после завершения наблюдается, но **не используется как
доказательство release**. До перезапуска API отдельная native-утилита читает
сохранённые квитанции и проверяет выход процесса через штатный OS adapter.
Старые readerId, PID и birth остаются теми же. Все три квитанции становятся
`released=true` по подтверждённому выходу ОС.

При этом `filesClosed=false` закономерен: убитый процесс не успел записать
штатное подтверждение закрытия. Reason `process-exited` вместе с проверенной
OS identity отличается от штатного `files-closed`. Протокол также предусматривает
`pid-reused`, но принудительное переиспользование PID этим тестом не создавалось.
`unknown_reader`, timeout и потеря связи не выдаются за положительную квитанцию.

Квитанции второго процесса остаются активными. Его время действительно
продвигается после завершения первого, файл сохраняется. Тестовый writer
продолжает загрузку: дописывает подтверждённые данные с 12 до 16 s и передаёт
новую ревизию второму плееру. Старые байты, sessionId/generation и writer
instance не подменяются.

## Перезапуск и защита нового воспроизведения

Первый плеер запускается снова из того же EXE и профиля. Драйвер не удаляет
stale sockets/locks или квитанции перед перезапуском: проверяется штатное
восстановление endpoint и profile ownership после выхода прежнего процесса.
Перезапущенный API находит все три прежние освобождённые квитанции.

Тот же источник с увеличенным подтверждённым диапазоном реально открывается
с **новым readerId и новой OS process identity**. Проверяются прежний физический
fileId/device, playing, движение clock и decoder I/O. Старый readerRelease
возвращает старую квитанцию и сохраняет новое воспроизведение. Cancel со старым
readerId отклоняется как reader_mismatch, старый probeId получает unknown_probe.
После forget старой группы unknown_reader проверяется только как результат
явного удаления уже подтверждённой квитанции.

Затем оба текущих воспроизведения освобождаются штатным API. Каждое даёт
положительный filesClosed; после первого закрытия второй reader ещё активен.
Только после освобождения всех endpoints и проверки пустых реестров удаляется
тестовый исходник. SHA всего опубликованного префикса проверяется до удаления.
Внутренние bridge receipts могут автоматически удаляться после их закрытия;
штатный release подтверждается внешней положительной квитанцией группы.

## Воспроизведение и сохранность

Общий сценарий: `tests/progressive_player_crash_recovery.py`.
Qt CTest: `progressive-player-crash-recovery` (timeout 300 s), с настоящими
`foxicmp-qt`/`FoxicMPq.exe` и native `foxicmp-progressive-reader-tests`.
Linux запускается через `qt/tests/run_tests.sh`: частные X11/D-Bus/PulseAudio,
отдельные профили, mute и software output, без доступа к микшеру пользователя.
Для Classic используются две временные portable-копии с предварительно
выключенной регистрацией контекстного меню.

Сверены SHA-256 установленных EXE/INI, всех построенных production EXE и
частной winpthreads DLL: они не изменились. Установленный Linux EXE уже совпадает
с проверенным; повторная замена не нужна. Сохранены 158 Classic shell entries,
Harvester не изменялся. Одноразовая Windows-задача, staging-копии, собственные
тестовые процессы, профили, sockets/locks и reader directories удалены.

## Что остаётся открытым

Это ограниченный player-crash срез четырёх RF64-профилей, без complete/EOF.
Повторное открытие не означает восстановления прежней позиции, ручной паузы
или выбранных дорожек после аварии. Не проверялись writer crash, оборванная
запись блока, disk full, reboot, rename/переход на итоговый файл, смешанные пары
редакций, полная codec/container matrix, длительная нагрузка или физическая A/V
синхронизация. Эти пункты остаются в [чеклисте](ProgressiveCompletionChecklist.md).
