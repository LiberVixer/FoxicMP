# Continuous AAC: шесть профилей и независимость истории Classic

Новый функциональный срез расширяет ordinary-main проверку AAC-LC: по пять
сценариев для шести профилей в каждой редакции. Используются bundled SDK 1.84,
обычные плееры и отдельные профили. YouTubeHarvester не изменяется.
[Результаты, SHA, исходные отказы и exit codes](ProgressiveContinuousAacProfilesValidation-2026-11-07.json).

## Итоговый повтор

| Редакция | Функциональные cases | Exit | Max RPC, s | Max resume, s |
|---|---:|---:|---:|---:|
| Linux Qt | 30 | 0 | 0.541 | 0.255 |
| Windows Qt | 30 | 0 | 0.485 | 0.203 |
| Windows Classic | 30 | 0 | 0.297 | 0.266 |

Обычная история Classic: ещё 2 PASS, native exit 0. Во всех финальных сериях
записано 0 independent decoder-buffer событий; прежний единичный отказ
мгновенного observer сохранён отдельно. Final source SHA тела теста одинаков
для трёх редакций и дополнительного старого Classic с позицией 37 s.

## Найденная ошибка Classic

При включённых `KeepHistory` и `RememberFilePos` разные continuous jobs
использовали один внутренний путь `continuous-video.mp4`. Classic читал и
сохранял под ним позицию как под именем обычного файла. В первом полном
прогоне независимые 120-секундные задания последовательно стартовали с
0.228 s, **41 s**, затем третье достигло EOF во время проверки другого job.
Qt начинал каждое задание с начала. Classic сохранил 12 успешных сценариев
перед отказом; этот прогон остаётся FAIL.

Отдельный детерминированный повтор записал в историю **тестовой копии** этот
путь с позицией 37 s. Прежний production EXE действительно начал новый job
ровно с **37 s**, native exit 1. Длительность контрольного файла не увеличивалась
для обхода ошибки, история в тесте не отключалась.

Исправление исключает именно continuous `CHarvesterSession` из чтения и
сохранения истории. Обычные файлы и другие native-progressive источники
сохраняют прежний путь работы с историей; существующие записи не удаляются.
`SaveHistory()` при закрытии вызывается до сброса активного session adapter.
Контракт API, SDK, названия редакций, настройки пользователя и тема не меняются.
Qt уже пропускает чтение и сохранение позиции при `preparedPlayback`
в `window.cpp`; Qt-код не требует этого исправления.

Регрессия проверяет старт каждого нового независимого задания раньше 2 s
и неизменность старой записи с позицией 37 s после каждого из шести профилей.
Дополнительный Windows Classic тест дважды открывает обычный завершённый
fMP4 с сохранённой позицией 37 s, ставит его на паузу, закрывает через API и
проверяет сохранение/повторное восстановление позиции и filesClosed receipts.

## Матрица профилей

| Профиль | AAC | Видео H.264 | Особенность |
|---|---|---|---|
| 48000-mono | 48 kHz, mono | 25 fps, B2 | Неполный последний AAC frame |
| 48000-stereo-fractional | 48 kHz, stereo | 30000/1001, B3 | Дробная частота кадров |
| 44100-mono | 44.1 kHz, mono | 25 fps, B2 | Другая частота аудио |
| 44100-stereo-b16 | 44.1 kHz, stereo | 60000/1001, B16 | Глубокая перестановка видео |
| aligned-control | 48 kHz, mono | 25 fps, B0 | 191488 presentation samples, ранний audio EOF |
| one-sample-audio-first | 44.1 kHz, mono | 25 fps, B2 | Один presentation sample, audio-first |

Основной source имеет 24 s видео; независимый playing endpoint — 120 s.
Оба остаются на тех же PID на протяжении всех шести профилей. Источники
дописываются физически, исходные SHA проверяются, неопубликованный хвост
не предоставляется reader.

Каждый профиль проверяет:

1. Header wait на четырёх байтах, подтверждённый partial prefix, достижение
   хвоста и реальную паузу writer не менее 10 s. Затем ручную паузу, физическую
   допись без публикации, публикацию без самовольного resume, явный resume
   менее 2 s, complete, paused seek 18/1/22 s и настоящий EOF.
2. Cancel на ручной паузе и три повтора старой Play-команды без нового playback.
3. Убийство только собственного worker по проверенной идентичности во время
   buffering; автоматический release до Cancel менее 2 s; явный retry с новым
   playback/reader ID после дописи writer.
4. Замену paused AAC обычным завершённым video-only fMP4 и устойчивость новой
   сессии к поздним Stop/Cancel/readerRelease старого задания.
5. Ошибку обязательной audio track на паузе, в том числе после раннего audio EOF;
   закрытие decoder/source, положительные filesClosed receipts и удаление cache.

После complete сравниваются payload SHA, PTS/DTS и duration всех video packets;
для AAC — payload SHA и PTS/DTS. Это проверка неизменности кодированных данных
и временных меток, **не** измерение физической синхронизации звука и картинки.
Linux Qt использует частный PulseAudio через `qt/tests/run_tests.sh`; Windows
Qt — WASAPI с частным профилем и нулевой громкостью, Classic — Null Audio
Renderer только в отдельной тестовой копии. Для одноотсчётного звука Qt может
уже закрыть AO; AAC codec, PCM window и независимый video playback обязательны.

## Исправления стенда до итогового повтора

Сохранены прежние неуспешные запуски, которые не объявляются product failures:

- FFmpeg не выбирал muxer по расширению `ordinary.fmp4`; имя заменено на
  `ordinary.mp4` при прежних явных fragment flags.
- В audio-first источнике первые обязательные AAC packets физически лежат
  после выбранной 12-секундной video boundary. Теперь сначала подтверждается
  честное ожидание audio, затем публикуется следующий подходящий prefix.
- Worker мог завершить output между status и heartbeat. `continuous-closed`
  допустим только после повторного status с подтверждённым complete без error.

После этих исправлений Qt обеих ОС прошёл по 30 сценариев. Последующий
Classic FAIL уже выявил реальную ошибку истории и привёл к изменению плеера.

Ещё один повтор Classic остановился после 20 успешных cases на `aligned-control`.
Диагностика показала честное buffering, позицию 0, применённый PCM window и
producer waiting без ошибки. Два AAC packets с PTS 3.946667/3.968 s находятся
по смещениям 285883/287706; опубликовано только 260724 bytes. Demux ждёт эти
пакеты и ещё не даёт 10 s video, необходимых штатному стартовому буферу Classic.
Это не основание читать неопубликованное или объявлять audio EOF.

Итоговый тест учитывает физические концы всех AAC packets с DTS до 10 s,
которые могут задержать demux перед стартом, и отдельно первые два packets
для PCM handshake. Перед дописью проверяется настоящий waiting в пределах
старого prefix: PCM plan может уже быть готов, хотя video startup buffer ещё
недостаточен. Для такого Windows fixture публикуется следующий 16-секундный
video prefix; остальные границы выбираются по фактическим packet offsets.
Исходный отказ и отдельный диагностический повтор сохранены как exit 1.

Следующий повтор дошёл до resume этого профиля: readyEnd=19 s, position=14.036 s,
запас 4.964 s при штатном пороге Classic 5 s. Сохранён ещё один exit 1.
Для стартового prefix 16 s тест теперь дописывает до video boundary 22 s,
вместо прежних 20 s; при стартовых 12 s прежние 20 s достаточны. Это остаётся
неполный source. Пороги Classic 10 s на старт и 5 s на resume не менялись;
проверка resume <2 s начинается после публикации достаточного partial input.
Для обоих уточнений программа не менялась.
Также сохранён отказ промежуточного observer: два Windows теста увидели
`acceptedRevision=2`, `appliedRevision=1` и ещё прежний header wait. Теперь
ожидание проверяется после применения нужной revision и нового запроса за
старую границу, а не по одному совпавшему `producerCode=waiting`.

В Linux независимый завершённый источник однажды сообщил `buffering` с
прежним playback/reader ID, активным decoder и пустой error. Старое требование
`playing` в каждом мгновенном снимке сохранило FAIL. Итоговый функциональный
observer отдельно записывает такие decoder stalls, требует возвращения к
`playing` менее чем за 2 s, не допускает pause/error/закрытия или смены identity
и обязательно завершает профиль на играющем endpoint. Это явно иной критерий
наблюдения, не PASS прежнего мгновенного условия и не stress-приёмка.

Для окончательного сравнения используется одна версия тела теста; старый EXE
дополнительно проверен тем же oracle с предварительной записью 37 s.

Linux попытка итоговой серии прервалась после 16 cases без final result
и без native exit: после возобновления работы её процессы и exec session
уже отсутствовали. Причина прерывания неизвестна. Эта попытка не засчитывается;
Linux повторяется полностью с тем же SHA тела теста. Оставшиеся private leases
очищены после native process-exited/files-closed proof, удалены только каталоги
прерванного теста. Windows результаты сохраняются отдельно.

## Границы результата

Это функциональная матрица AAC-LC mono/stereo 44.1/48 kHz, не полный stress,
не все AAC layouts/codecs и не фактическая интеграция Harvester. Новые проверки
не закрывают прежние Linux release outliers, MPCVR Event growth, зависший OS
I/O, многочасовую нагрузку или физические A/V критерии 80/40 ms.

Исправленная Classic собрана отдельно обычным MSVC production link, без test
hooks. Опубликованные assets/tag `progressive-api-v1.84` не перезаписываются.
Qt EXE не менялись, поэтому новая установка Linux не требуется. В исходном baseline из 583 файлов неизменны 582. Установленный Linux INI
сохранялся в 03:21 UTC, до запуска окончательного Linux-повтора в 05:56 UTC;
кто выполнил то сохранение, не устанавливалось. Тесты используют частные
профили и не записывали установленный INI. Текущий профиль включён в отдельный
конечный baseline из 583 файлов и сохраняется без восстановления старой версии.
Первоначальные SHA и время наблюдения остаются в отчёте.

Воспроизведение: `tests/progressive_aac_package_test.py --scenario aac-profile-resilience` с обычными `--edition`, `--player`, `--sdk-directory`,
`--reader-runner`, `--report-directory`. Отдельная регрессия обычной истории:
`tests/progressive_classic_history_test.py` с теми же путями без `--edition` и
`--scenario`. Windows graph tests запускаются из интерактивного сеанса
одноразовой задачей; Linux — только частным X11/D-Bus/PulseAudio wrapper.
