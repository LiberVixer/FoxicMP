# Просмотр локальных дорожек Harvester во время загрузки

Состояние на 2026-10-09: экспериментальная реализация для Windows x64.
Она не входит в опубликованный стабильный релиз 1.9.1.75. Рабочий профиль
в `C:\FoxBroxer\Prg\MPMY` при разработке и испытаниях не менялся.

## Что реализовано

FoxicMP принимает `/harvester-session <путь к session.json>`. Видео и аудио
открываются в одном DirectShow-графе через отдельные локальные readers.
Плеер использует подтверждённые байты загрузчика и не получает исходный URL.
Чтение обычных файлов и параметр `/dub` сохраняют прежний маршрут.

Адаптер `scripts/progressive_download.py` в исходниках Harvester запускает два
native HTTP-загрузчика yt-dlp параллельно. Выбранные форматы, cookies, заголовки,
proxy, повторы и обычные postprocessors сохраняются. При общем ограничении
скорости каждой дорожке выделяется половина лимита. Исходные дорожки используются
также для итогового объединения FFmpeg без повторного скачивания.
Для выбранного muxed HLS/VOD используется native HLS-загрузчик yt-dlp. Уже
скачанные и расшифрованные байты локального кэша передаются FFmpeg через stdin:
он разделяет H.264/AAC на две локальные fMP4-дорожки без перекодирования.
Начальный `moov` публикуется после первого пакета: параметры AAC из MPEG-TS
успевают попасть в заголовок. Плеер читает эти дорожки; FFmpeg предварительного
просмотра не получает URL.

В текущем интерфейсе Harvester интеграция приостановлена: кнопок FoxicMP нет,
а `script_environment()` выставляет `YTD_PROGRESSIVE_PLAYBACK=0`, включая ранее
сохранённое включение. Протокол и адаптер доступны для отдельного испытания.
Нельзя считать эту сборку готовой пользовательской интеграцией Harvester.

## Поддерживаемый набор

- Windows, одна видеодорожка MP4/H.264 `avc1` и одна аудиодорожка M4A/AAC-LC `mp4a.40.2`.
- Обычные MP4 с полным `moov` перед медиаданными, целым индексом пакетов,
  доступным первым ключевым кадром и известной положительной полной длиной.
- fMP4 с начальным `moov/mvex/trex`, одной дорожкой, `tfhd/tfdt/trun`.
  Индекс пополняется только после подтверждения целой пары `moof + mdat`.
  Фрагмент может быть неполным при загрузке; неполный окончательный файл
  отклоняется. Для fMP4 требуется положительная `duration100ns`;
  `expectedTotalBytes:null` допускается до подтверждения конечной длины.
- Последовательная запись дорожек. Native HTTP fMP4 (включая selected DASH
  URL) и непрерывный muxed HLS/VOD через описанный локальный адаптер.
- Локальный фиксированный диск Windows, пути до 240 символов. UNC, URL,
  alternate data streams, переходы через reparse points и совпадающие файловые
  идентификаторы аудио/видео отклоняются.
- Не более двух миллионов пакетов в каждой дорожке; `moov` до 64 MiB.

HE-AAC, xHE-AAC, HEVC, VP9, AV1, HLS с отдельными rendition-дорожками,
HLS discontinuities, live, DRM, несколько аудиодорожек,
переключение дорожек и `moov` в конце не входят в проверенный набор.
Неподходящие форматы продолжают обычное скачивание выбранного качества.
Плеер не запрашивает недостающие сетевые диапазоны.

## Поведение воспроизведения

Граница готового буфера вычисляется по целым пакетам обеих дорожек, их PTS/DTS
и общей временной шкале. MP4 edit lists и отрицательное начало AAC сохраняются;
граница учитывает переупорядоченные видеокадры. Проценты байтов не переводятся
линейно в секунды. На таймлайне показывается общая доступная часть.

Начальный запас — 10 секунд, возобновление — 5 секунд, остановка продвижения —
при запасе меньше секунды. Короткие полностью завершённые дорожки могут играть
без начального десятисекундного запаса. При нехватке одной дорожки граф ставится
на паузу; отсутствие данных 60 секунд не считается успешным EOF.
Ручная пауза сохраняется. Перемотка за готовую границу при загрузке отклоняется.

Stop и Close отменяют ожидания readers и освобождают граф. Stop завершает
прогрессивный просмотр; для нового просмотра нужно открыть манифест заново.
Достижение конца MP4-индекса само по себе не отправляет EOF: splitter ждёт
`complete` своей дорожки. Это ожидание также прерывается Stop, Close и flush.
Ошибка открытия прогрессивного источника не переключает обычный плейлист;
переход вперёд/назад в пустом плейлисте безопасно отклоняется.
Новая `generation` закрывает старый граф с диагностикой. Автоматическое
переоткрытие новой генерации пока не реализовано: его запускает пользователь.
После объединения плеер продолжает читать исходные дорожки, без автоматического
переключения на итоговый файл.

## Протокол и время жизни файлов

Схема JSON — `schemaVersion=1`, случайный `sessionId` из 32 hex-символов,
положительные `generation`/`revision`. Есть ровно две записи `tracks.video`
и `tracks.audio`: plain filename, container, `availablePrefixBytes`,
`expectedTotalBytes`, `initializationReady`, state. Дополнительный bool
`fragmented` разрешает неизвестную длину fMP4; финальное `complete` требует
подтверждённой длины. `duration100ns` задаёт длительность фрагментированного
источника; `timestampOffset100ns` задаёт общий сдвиг обеих дорожек. Локальный
HLS-адаптер добавляет секунду к общей шкале и плеер вычитает её; относительные
PTS/DTS видео и аудио сохраняются, в том числе отрицательное начало AAC.

JSON записывается атомарной заменой уникального временного файла после
подтверждённой записи данных. Читатели JSON в Windows разрешают DELETE sharing;
краткий конфликт со старым читателем обрабатывается ограниченным повтором.
Префикс в одной генерации не уменьшается; известная длина и имена не меняются.
Неизвестная длина fMP4 может один раз стать известной положительной длиной.
Повторные и старые ревизии игнорируются. Размер JSON/IPC ограничен 64 KiB,
типы, диапазоны, повторные ключи и переполнения проверяются.

Имена и права локального named pipe ограничены SID текущего пользователя.
FoxicMP проверяет пользователя процесса сервера; сервер сверяет PID клиента
с Win32 API. Сообщения `attached`, `buffering`, `playing`, `paused`, `error`,
`released` содержат идентификаторы сеанса и версии. Heartbeat поддерживает
связь даже при остановке записи. Потеря связи вызывает общую буферизацию,
а не EOF; чтение можно остановить. Cookies и исходные URL в манифест не попадают.

Дорожки открыты с READ/WRITE sharing и без DELETE sharing: их пути остаются
закреплены до закрытия всех readers. Независимый provider сохраняет leases
по PID и времени создания процесса. Разрыв pipe сам по себе не означает release.
После аварии lease снимается лишь при подтверждённом завершении процесса
или смене его идентичности. Неопределённый результат проверки сохраняет lease.

Объединение не переименовывает исходные дорожки. Запись успешной загрузки
в архив выполняется только после обычной успешной обработки итогового файла.
При ошибке/отмене дорожки остаются для диагностики. После успешной сборки provider
удаляет только исходные дорожки, когда нет readers/подключений: через 30 секунд
после последнего клиента или через 600 секунд, если просмотр не открывали.
Итоговый файл сохраняется. Папка `foxicmp-sessions` исключена из общей очистки
временного каталога Harvester.

## Отдельный запуск для проверки

Нужны обновлённые исходники Harvester, Python с его закреплённой версией yt-dlp
и FFmpeg; стабильный EXE Harvester не получает новые модули автоматически.
Запускайте адаптер с теми же аргументами yt-dlp и выбранными форматами:

```powershell
$env:YTD_TEMP_DIR = 'E:\FoxicMP-test\temp'
python E:\Harvester\scripts\progressive_download.py --load-info-json E:\FoxicMP-test\input.json -f 137+140 --ffmpeg-location E:\FFmpeg\bin -o E:\FoxicMP-test\finished.mp4
```

Это пример для собственного info JSON с соответствующими format IDs.
Сообщение `[FoxicMP]` в stdout сообщает путь и готовность. Когда `ready=true`,
откройте просмотр в отдельном экземпляре новой сборки:

```powershell
E:\Programs\MPMY-src\_bin\FoxicMP_x64\FoxicMP64.exe /new /harvester-session E:\FoxicMP-test\temp\foxicmp-sessions\<id>\session.json
```

Для изоляции профиля копируйте EXE, нужные библиотеки и portable INI в отдельную
тестовую папку. Не подменяйте установленный плеер ради проверки.

## Воспроизводимые проверки

Проверка схемы, версий, временных меток, переполнений и границы целых пакетов:

```sh
g++ -std=c++17 -Isrc tests/harvester/state_tests.cpp -o state-tests
./state-tests
```

В каталоге Harvester:

```sh
.venv/bin/python -m unittest tests.test_progressive_playback tests.test_progressive_http tests.test_progressive_gui tests.test_progressive_hls
```

HTTP-тест использует локальный сервер: оба запроса должны начаться параллельно,
каждый файл запрашивается один раз, заголовки сохраняются, FFmpeg объединяет
те же bitstreams. Отдельный тест намеренно вызывает ошибку FFmpeg и проверяет
сохранение источников и отсутствие успешной записи в архиве. Qt-тест работает
в отдельном процессе, чтобы не создавать второй QApplication в общей suite.

Windows harness требует интерактивный рабочий стол и отдельный portable-профиль.
Создайте сигнальные файлы в выбранной тестовой папке:

```powershell
python tests\harvester\make_fixtures.py --work E:\FoxicMP-test
python tests\harvester\windows_playback.py --harvester-root E:\Harvester --exe E:\FoxicMP-test\player\FoxicMP64.exe --work E:\FoxicMP-test --case stall
```

Остальные сценарии выбираются через `--case`. `windows_download.py` проверяет
полный путь HTTP → адаптер → плеер → FFmpeg → отложенная очистка. Он ожидает
в своей тестовой папке `scripts` Harvester, доступный Python-пакет `yt_dlp`,
`tools/ffmpeg.exe`, `tools/ffprobe.exe`, `player/FoxicMP64.exe` и сигнальные файлы.
Не запускайте harness с EXE рабочего плеера.

## Предыдущий этап: измерение A/V обычных MP4 (2026-10-09)

`windows_av_capture.cpp` захватывает звук только дерева тестового процесса
через WASAPI process loopback и яркость 8×8 пикселей в центре отображаемого видео.
Аудиопакеты и выборки изображения сопоставляются по QPC в единицах 100 ns.
Именно такую временную базу возвращает
[IAudioCaptureClient::GetBuffer](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer).
Сохраняются только яркость/амплитуда и время: записи микрофона и снимков рабочего
стола нет. Применён тот же отдельный portable-профиль, что в предыдущих тестах.

Сигнал: 90 s, H.264 25 fps с B-кадрами, AAC-LC 48 kHz; белая вспышка и тон
880 Hz длительностью 80 ms каждые 2 s. Дополнительно аудиофайл сдвинут на
+240/-240 ms через MP4 edit list. Для этих случаев контрольный обычный MP4
собран с `-copyts`: `/dub` нормализует начала отдельных файлов и не подходит
для проверки сохранения относительного смещения. Ранний просмотр сохраняет
заданный сдвиг; ошибка в таблице отсчитывается **от заданного сдвига**, а не от нуля.

Каждый ранний просмотр проходит старт с неполными файлами, опустошение общего
буфера, возобновление после дописывания и перемотку. Измеряются полные пары
импульсов. Частичный импульс при начальном открытии не учитывается; первые
800 ms после команды seek исключаются, поскольку seek может отрезать звук,
который расположен перед показанной вспышкой. В остальном отсутствующая пара
считается ошибкой. Некорректный timestamp, отсутствие аудио/вспышек или ошибка
захвата также не могут дать успешный результат.

| Режим | Сдвиг аудио | Полных пар | Максимальная ошибка | Верхняя граница с учётом выборки |
| --- | ---: | ---: | ---: | ---: |
| Обычный | +0 ms | 8 | 78.25 ms | 92.66 ms |
| Ранний просмотр | +0 ms | 19 | 73.26 ms | 90.61 ms |
| Обычный | +240 ms | 8 | 71.88 ms | 85.42 ms |
| Ранний просмотр | +240 ms | 19 | 67.36 ms | 82.17 ms |
| Обычный | -240 ms | 8 | 63.67 ms | 86.05 ms |
| Ранний просмотр | -240 ms | 18 | 70.12 ms | 84.22 ms |

Всего проверено 80 полных пар. Все шесть прогонов уложились в 100 ms даже
по консервативным границам: момент изменения пикселей ограничен последней
тёмной/первой светлой выборкой, аудио — соседними блоками примерно по 1 ms.
Флагов недействительного timestamp и разрыва аудиозахвата не было.
В последнем раннем прогоне максимальная ошибка: старт 68.73 ms,
возобновление 50.87 ms, после seek 70.12 ms.

Это измерение **программного выхода** на конкретной Windows-машине, а не
сравнение PTS внутри графа. Оно не включает аппаратную задержку монитора,
ЦАП и акустики. Для физического критерия ≤100 ms нужна отдельная запись
света экрана и звука одним измерительным устройством; она здесь не выполнена.

Воспроизведение и отчёты: `_bin/harvester-test/av-runs`, `av-summary.json`.
Четыре теста анализатора проверяют известные положительные/отрицательные задержки,
отсутствующий звук, недействительные timestamps и обрезанный импульс при seek;
все прошли.

Воспроизвести на отдельном интерактивном Windows-профиле (SDK 20348+):

```bat
rem В x64 Developer Command Prompt Visual Studio, из корня репозитория:
tests\harvester\build_av.cmd
python tests\harvester\make_fixtures.py --work E:\FoxicMP-test --audio-offset-ms 240 -240
python tests\harvester\windows_av.py E:\FoxicMP-test baseline
python tests\harvester\windows_av.py E:\FoxicMP-test progressive
python tests\harvester\windows_av.py E:\FoxicMP-test baseline 240
python tests\harvester\windows_av.py E:\FoxicMP-test progressive 240
python tests\harvester\windows_av.py E:\FoxicMP-test baseline -240
python tests\harvester\windows_av.py E:\FoxicMP-test progressive -240
```

Перенесите `av-capture.exe` в корень выбранной тестовой папки; её остальное
содержимое описано выше для `windows_download.py`. Окно должно быть видимым,
не перекрытым другим приложением. Использовать рабочий профиль нельзя.

## Предыдущий этап: обычные MP4 и fallback (2026-10-09)

Использован настоящий Windows Python/yt-dlp 2026.08.19, тот же CLI-адаптер,
FFmpeg 9.0.2 и тестовый FoxicMP x64. Интеграция GUI Harvester осталась выключенной.
Из-за неработающего DNS Windows использован временный CONNECT-прокси Linux,
ограниченный IP тестовой Windows-машины. Для VK в тестовый Python скопирован
пакет certifi из существующего окружения Harvester: проверка TLS не отключалась.
Системные DNS, сертификаты и рабочий профиль плеера не менялись.

`windows_sources.py` проверяет окончание скачивания, запись в архиве, H.264/AAC
в итоговом MP4, длительность, затем реальные меняющиеся пиксели и ненулевой
звук процесса при обычном воспроизведении. При двух сохранённых дорожках
сравнивается SHA-256 их демультиплексированных packet payloads с итогом:
объединение не должно перекодировать или менять bitstreams. Signed URL и
учётные данные в отчёт не включаются.

| Источник | Выбранные форматы | Итог | Ранний просмотр | Проверка готового файла |
| --- | --- | --- | --- | --- |

и работоспособность готового результата. `auto` регистрирует оба варианта.


Первое ожидание раннего просмотра YouTube не подтвердилось: реальная структура
файлов оказалась fMP4. Этот результат сохранён, затем отдельно проверены
обычное воспроизведение готового результата и неизменность обеих дорожек.
Первая попытка Rutube упёрлась в 300-секундный лимит тестового harness;
повтор продолжил сохранённые HLS-фрагменты, с лимитом 900 s и четырьмя потоками.
Первая попытка VK показала отсутствие нужного CA в тестовом Windows Python;
повтор использовал certifi и обычную проверку TLS.

Таким образом, ранний просмотр реальных YouTube/VK в этой выборке **не
подтверждён**. Их HTTP MP4 оказался фрагментированным, а Rutube использовал HLS.
На этом этапе эти варианты были исключены из MVP; поддержку fMP4/HLS добавили
после выявления этого ограничения (описание выше). Скачивание и просмотр готового файла
продолжают работать; нельзя объявлять поддержку раннего просмотра сайта
только по codec/extension или успешному извлечению URL.

## Дополнительные проверки fMP4/HLS (2026-10-09)

Итоговая сборка Windows x64: SHA-256
`3023bafc8adacdac2070b7b1c43a8b76f038ec8bd8189c7243ec8fe6813cf6dd`.
Дисковые чтения фрагментного индекса выполняются вне mutex, используемого UI.
Плеер по-прежнему не получает URL и не запрашивает недостающие байты.
Описания H.264/AAC для `empty_moov` создаются из записи codec description,
а первый диапазон пакета берётся из проверенного растущего индекса.
Bento4 при прогрессивном открытии останавливается после `moov`: статический
список первых фрагментов не используется для быстрого поиска. Перемотку
обслуживает текущий растущий индекс. Отдельный Windows C++-тест подтвердил
отсутствие чтения `moof/mdat` в этом режиме и прежний индекс обычного MP4.
В Visual Studio x64 Developer Command Prompt его можно повторить так:

```bat
tests\harvester\build_bento.cmd E:\FoxicMP-test\video-fragmented.mp4 E:\FoxicMP-test\video.mp4
```

Захват перепроверяет текущий HWND после загрузки, проверяет владельца области
экрана и убирает курсор за пределы окна. Перекрытие или лишняя видимая вспышка
отклоняют замер; они не превращаются в успешный результат анализатора.

На сигнальных fMP4 проверены старт, возобновление после буферизации и перемотка.
Сдвиг звука +240/−240 ms сохранён в общей шкале:

| Сдвиг звука | Полных пар вспышка/сигнал | Максимальная ошибка | Верхняя граница с неопределённостью |
| --- | --- | --- | --- |
| 0 ms | 19 | 73.52 ms | 88.55 ms |
| +240 ms | 19 | 70.78 ms | 84.98 ms |
| -240 ms | 19 | 74.64 ms | 88.64 ms |

Порог 100 ms выдержан во всех трёх фазах каждого запуска. Это программное
измерение WASAPI/GDI на общей QPC-шкале; физическая задержка монитора и колонок
таким измерением не определяется. Полные записи пар — в локальных JSON/CSV
`_bin/harvester-test/av-runs`. Во всех трёх запусках флагов discontinuity аудио нет.

Сигнальные файлы и индексы воспроизводятся с сохранением отрицательного начала
AAC и общего сдвига +1 s:

```bat
python tests\harvester\make_fixtures.py --work E:\FoxicMP-test --audio-offset-ms 240 -240 --fragmented
python tests\harvester\windows_av.py E:\FoxicMP-test progressive 0 fragmented
python tests\harvester\windows_av.py E:\FoxicMP-test progressive 240 fragmented
python tests\harvester\windows_av.py E:\FoxicMP-test progressive -240 fragmented
```

Дополнительно прошли C++-валидация неизвестной длины и её однократного
подтверждения; 7 тестов анализа/индекса fMP4; 16 тестов адаптера Harvester.
На реальных исходных VK-дорожках все 49 581 видео- и 92 967 аудиопакетов
совпали с FFprobe по диапазону, размеру и PTS/DTS.
Локальный HTTP/HLS-тест подтвердил один запрос каждого сегмента, готовность
просмотра до последнего запроса, идентичность bitstreams и относительных PTS/DTS
предварительного и итогового файлов. Ошибка окончательного HLS-preview не
прерывает обычный путь скачивания.

Отдельный Windows-тест `windows_openerror.py` воспроизводит AAC без
AudioSpecificConfig в раннем `moov`. Ошибка открытия освобождает lease,
плеер остаётся жив и закрывается штатно. Исходный сбой `SetNext` пустого
плейлиста воспроизводился на Rutube; защищены оба направления навигации,
а прогрессивный источник исключён из перехода к следующему файлу при ошибке.

Windows-стресс-тест атомарной публикации JSON выполнил 1000 обновлений с двумя
читателями (shared DELETE и старый CRT-читатель): ошибок чтения и регресса
ревизий нет, временные файлы удалены.

## Дополнительные проверки отказов перед предварительным релизом

На той же сборке прошли шесть сценариев для обычного MP4 и fMP4:
аварийное завершение provider и его перезапуск, аварийное завершение писателя,
удаление подтверждённых байтов через усечение тестовой дорожки. При потере
provider позиция остаётся неподвижной, lease и файлы сохраняются; после его
возвращения тот же граф продолжает просмотр. Смерть писателя публикует `failed`,
освобождает граф и сохраняет файлы. Усечение подтверждённых данных завершает
граф с ошибкой, без падения или зависания окна. Это моделирование потери данных,
а не испытание физически неисправного диска или нехватки места.

Portable ZIP распакован в отдельный каталог: прошли `/dub` и прогрессивное
открытие с начальной буферизацией. EXE совпадает с измеренной сборкой по SHA-256.

Снимок командного адаптера и самостоятельные 13 тестов включены в
`tools/harvester-preview`. Он не включает интерфейс или Harvester.exe.

ещё не проверены. Проверка выбранных публичных форматов не означает поддержку
всех вариантов качества и контейнеров этих сайтов.
